# 02 · 架构与代码地图

> 本文描述 Eropic 的整体分层、数据流、包结构与关键约束。功能级的"怎么实现、代码在哪"见 `04-功能索引.md` 与 `features/` 下的功能开发文档。

## 1. 分层

```text
┌──────────────────────────────────────────────────────┐
│ UI 层（Compose）                                      │
│  Screen（无状态） · UiState · 事件回调                 │
├──────────────────────────────────────────────────────┤
│ ViewModel 层（androidx.lifecycle）                     │
│  StateFlow<UiState> · 分页 · 权限状态 · 一次性事件      │
├──────────────────────────────────────────────────────┤
│ Repository 层（单例，AppContainer 注入，ADR-0007）      │
│  MediaRepository · TrashRepository · FileOps · Settings│
├──────────────────────────────────────────────────────┤
│ DataSource 层                                         │
│  MediaStoreDataSource · Room DAO · FileSystem/SAF      │
├──────────────────────────────────────────────────────┤
│ 后台任务（WorkManager + CoroutineWorker）              │
│  MediaSyncWorker · AnalysisWorker · TrashCleanupWorker │
└──────────────────────────────────────────────────────┘
```

约束：
- UI 只依赖 ViewModel；ViewModel 只依赖 Repository；Repository 编排 DataSource。
- 不允许 UI 直接查 MediaStore/Room；不允许 Worker 直接改 UI 状态（写 Room，UI 观察）。
- 单向数据流：事件上行，状态下行。

## 2. 事实源与缓存

| 存储 | 角色 | 丢了会怎样 |
|---|---|---|
| **MediaStore** | 媒体文件的权威来源（系统维护，增量、含 EXIF 基础字段） | 不能丢，必须只读使用 + 变更监听 |
| **Room** | 应用索引：元数据、哈希、分组、回收站、操作日志、计数 | 可重建（重新扫描）；但回收站状态丢失有风险，需备份表 |
| **缩略图磁盘缓存** | 256/512px WebP，LRU 512MB~2GB | 可丢弃，按需重生成 |
| **DataStore** | 用户设置：排序、列数、扫描范围、保留天数、阈值 | 可重置，但体验受损，应随导出/备份 |
| **操作日志（Room）** | 每次移动/重命名/删除的原路径与结果，支持撤销与恢复 | 不可丢（写操作前先落盘） |

冷启动数据流：

```text
MainActivity
  └─ PermissionGate（检查 READ_MEDIA_IMAGES / 14+ 部分授权）
       └─ AppStartup（读 DataStore，判断是否首次/需要增量同步）
            ├─ 首屏：Room 分页查询（已索引部分）→ 立即出图（占位符）
            └─ SyncWorker：MediaStore generation 检查 → diff → 批量 upsert Room
                 └─ Room invalidation → Paging 自动刷新
```

首屏目标是"先有再全"：索引未完成时也应有可用的图库（已扫到的先显示，顶部显示进度）。

## 4. 线程与任务规则

- Room 读写、MediaStore 查询、文件 IO、哈希/解码：`Dispatchers.IO`（通过 `AppDispatchers` 注入，便于测试与限流）。
- 哈希并行度：默认 `min(4, CPU 核数/2)`；低端机/内存紧张降到 2，并分批 64 张流式处理。
- 主线程零 IO：不做查询、解码、文件 stat；Compose 中不直接读 DB。
- 长任务统一 WorkManager：可设"仅充电/空闲"约束；进度写 Room + WorkInfo；杀进程后可恢复。
- FGS：Android 14+ 必须声明 type（索引用 `dataSync`）；Android 15 起 6 小时/24 小时配额，任务必须可暂停/恢复、分批 checkpoint。
- 取消：协程检查点用 `ensureActive()`；文件操作"先写 pending 日志再动手"，异常时按日志回滚或标记"未完成"。

## 5. 大库红线（10 万~30 万张）

1. 禁止 O(n²) 全量两两比较；必须 size bucket + hash band 裁剪。
2. 禁止为全部图片预生成缩略图；只按需生成 + LRU。
3. 禁止 `COUNT(*)` 全表；维护 `CounterEntity` 或在扫描时增量累加。
4. 禁止主线程查询；禁止在列表 item 里做解码/stat。
5. 列表必须给 stable key（`contentId` 或 `path`）与 `contentType`；分页 limit 200~400。
6. 每次扫描必须可断点恢复（记录 lastMediaId / generation），不能"失败重来"。
7. 写操作必须幂等：同一目标路径重复执行不产生副本或覆盖。

## 6. 权限与能力分层

- M0（只读）：`READ_MEDIA_IMAGES`（13+）、`READ_MEDIA_VISUAL_USER_SELECTED`（14+ 部分授权）。
- M3（写）：侧载分发 → 直接申请 `MANAGE_EXTERNAL_STORAGE`（ADR-0012），由 `StorageAccess.hasAllFilesAccess()` 探测；未授予时写入口统一置灰并说明原因，读取/查重/预览不受影响。
- 备选（未采纳）：`MANAGE_MEDIA`（Android 11+ 特殊权限，仍需用户在设置里开启且系统回收站保留期不可控）、MediaStore `createWriteRequest/createTrashRequest`（批量时逐次系统弹窗）。
- 永远不做"没有权限却假装成功"：所有写操作前检查能力，失败给出可操作提示。

## 7. 功能 → 代码

统一维护在 `04-功能索引.md`：每个规划功能编号（A-01/B-05/C-03…）对应里程碑、计划代码入口、当前状态。
功能开发文档（`features/<编号>-<名称>.md`）必须含"代码地图"小节，格式：`app/src/main/java/.../MediaScanner.kt#scanIncremental()`。

## 8. 模块化演进

- M0~M1 单模块 `:app`：编译快、改动力气小，适合单人 + AI 协作。
- 触发拆分：单次增量编译 > 60s、或需要独立测试媒体层、或要复用 UI 组件。
- 目标结构：`:core:model` / `:core:database` / `:core:media` / `:core:ui` / `:feature:*`。
- 约束：feature 之间不直接依赖；跨 feature 用导航 + 共享 repository；`core` 不依赖 `feature`。

## 9. 测试策略

| 层 | 方式 | 重点 |
|---|---|---|
| 纯逻辑 | JUnit（无 Android 依赖） | Hamming/band 候选、筛选条件、冲突命名、路径映射、EXIF 方向 |
