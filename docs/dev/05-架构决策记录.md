# 05 · 架构决策记录（ADR）

> 记录"为什么这样选"，避免以后反复讨论或无意推翻。新决策追加编号，旧记录只改状态（如"已废弃/被 0007 取代"），不删除。
> 格式：状态 / 日期 / 背景 / 决策 / 理由 / 后果 / 备选。

## ADR-0001：单模块 `:app` 起步

- 状态：已采纳（2026-10-27）
- 背景：单人开发 + AI 辅助；M0~M1 需要快速迭代；过早拆模块会增加 Gradle 配置与跨模块依赖成本。
- 决策：M0~M1 使用单模块，按包分层（`core/`、`feature/`、`ui/`），包间依赖方向固定。
- 理由：编译快、重构成本低；包结构已按未来模块边界划分，拆分时主要是移动目录。
- 后果：单模块编译时间会随代码增长；触发拆分条件：增量编译 > 60s、媒体层需独立测试、UI 组件需复用。
- 备选：一开始就多模块（更规范，但早期收益低）；按功能拆（feature 间共享成本高）。

## ADR-0002：M0 只申请只读媒体权限，写权限推迟到 M3 决策

- 状态：已采纳（2026-10-27）；M3 需复核
- 背景：项目不上架、GitHub 开源 + 侧载；Android 13+ 用 `READ_MEDIA_IMAGES`，14+ 有"部分授权"；写操作（移动/回收站）需要额外能力（`MANAGE_MEDIA` 或全文件访问）。
- 决策：
  - M0 只声明并申请 `READ_MEDIA_IMAGES` + `READ_MEDIA_VISUAL_USER_SELECTED`；
  - 不声明 `MANAGE_EXTERNAL_STORAGE`，M3 在 iQOO Neo8 上实测 `MANAGE_MEDIA` 的授予路径、ColorOS/OriginOS 差异后再定；
  - 所有能力通过 `StorageAccessRepository` 探测，UI 按能力降级（无写权限时隐藏移动/删除，只读展示）。
- 理由：M0 只需读；最小权限降低首次授权摩擦与用户疑虑；侧载虽无 Play 限制，但全文件权限在部分 ROM 上仍有额外弹窗与风险。
- 后果：M0 无法做写操作验证；部分授权（用户只选几张）会导致"图库看起来漏图"，必须做引导 UI。
- 备选：直接申请全文件访问（简单、能覆盖非媒体目录，但权限过重、开源项目口碑风险）；纯 SAF（10 万级性能不可接受）。

## ADR-0003：MediaStore 为权威源，Room 为可重建索引

- 状态：已采纳（2026-10-27）
- 背景：需要展示"所有图片"，且 10 万~30 万规模；系统 MediaProvider 持续维护媒体库（相机写入、下载、文件管理器复制都会触发索引）。
- 决策：
  - 读取路径：MediaStore（Images 表为主，必要时合并 Files 表）→ 增量 diff → 写入 Room 缓存；
  - Room 存元数据、哈希、分组、回收站、操作日志、计数，可由全量重扫重建；
  - 不用原始 `File` 遍历作为主通道（读不到 `Android/data`、SAF 逐文件慢）；
  - 变更检测：`MediaStore.getGeneration()` + `(contentId, dateModified)` 差分 + ContentObserver 防抖。
- 理由：可靠性、增量成本低、字段齐全；符合 Aves/Immich 等项目的成熟做法。
- 后果：`.nomedia` / 隐藏目录 / `Android/data` 天然不可见，需在 UI 说明并提供"包含隐藏目录"开关（仍受系统限制）；SD 卡拔插会导致 ID 漂移，用 path+size+mtime 兜底。
- 备选：全盘 File 遍历（受 scoped storage 限制，且与 MediaStore 结果不一致）；纯 MediaStore 不落库（无法做哈希/分组/大库分页）。

## ADR-0004：自建回收站为主，系统回收站兜底

- 状态：已采纳（2026-10-27）
- 背景：需要"删除进回收站、30 天可恢复"；系统 `createTrashRequest` 只对自身条目或 `MANAGE_MEDIA` 生效，保留期固定 30 天且出现在系统"最近删除"。
- 决策：
  - 抽象 `TrashRepository`；默认 `SelfBuiltTrash`：同卷改名到 `/sdcard/.EropicTrash/`（放 `.nomedia`，零拷贝）+ Room 记录原路径/删除时间/到期时间；
  - 无写权限或系统方案可用时降级 `SystemTrash`；
  - 恢复：改名回原路径，冲突加 `(1)` 后缀，再通知 MediaStore 重扫；永久删除二次确认。
- 理由：保留期/容量统计/UI 完全可控；改名毫秒级，适合大批量；Fossify Gallery 验证过该模式。
- 后果：卸载 App 前需提示清空回收站（否则残留）；跨卷只能复制；需防用户手动改 `.EropicTrash`。
- 备选：只用系统回收站（保留期不可控、无 MANAGE_MEDIA 时不可用）。

## ADR-0005：M0 只做图片；Android 12+；targetSdk 36 + 单 Activity Compose

- 状态：已采纳（2026-10-27）
- 背景：用户明确 M0 不做视频、最低 Android 12；本机 SDK 36、Android Studio 2025.2。
- 决策：
  - M0~M1 只索引图片（Images 表），视频列 P1/推迟；数据库保留 `mimeType` 字段，后续扩展不迁移主键；
  - `minSdk 31`；`compileSdk/targetSdk 36`；
  - 单 Activity + Navigation Compose + Material 3；targetSdk ≥ 35 强制 edge-to-edge，所有页面用 `Scaffold` + `innerPadding`；
  - 主题用 Material 3 动态取色（Android 12+ 支持）。
- 理由：减少 M0 变量；Android 12 起分区存储/媒体权限模型统一；Compose 单 Activity 是当前官方推荐。
- 后果：视频/RAW 需后置；targetSdk 36 的 edge-to-edge 若处理不好会遮挡内容，需在 M1 统一处理。
- 备选：支持 Android 11（需额外兼容代码，收益低）；多 Activity（返回栈/状态共享复杂）。

## ADR-0006：完全本地、无网络权限（v0.2 起部分被 ADR-0022 取代）

- 状态：已采纳（2026-10-27）
- 背景：个人 120GB+ 图库，隐私敏感；用户不需要云同步。
- 决策：Manifest 不声明 `INTERNET`；不做账号、统计、崩溃上传（崩溃日志仅本地文件，用户主动导出）。
- 理由：隐私是开源相册工具的信任基础；避免"照片被上传"的质疑；也简化合规。
- 后果：无法做云端备份/跨设备同步；分享走系统 `Intent`（由系统/其他 App 发起网络请求，与本 App 无关）。
- 实测（2026-10-27，debug APK 反查）：除本 App 声明的 3 个权限外，Manifest 合并还带入了 WorkManager 的 `WAKE_LOCK` / `ACCESS_NETWORK_STATE` / `RECEIVE_BOOT_COMPLETED` / `FOREGROUND_SERVICE`。这些是库的默认项，**没有 `INTERNET`，进程无法联网**；M1 若不需要可用 `tools:node="remove"` 裁掉。
- 备选：可选云备份（M5 之后，需单独设计加密与凭据管理）。

## ADR-0007：M0 用手写 AppContainer，不引入 Hilt

- 状态：已采纳（2026-10-27）
- 背景：脚手架由用户建好、我接手补齐依赖；M0 只有 4 个协作对象（Database / MediaRepository / SignatureGenerator / IndexCoordinator），且本机构建环境受沙箱限制，注解处理器越多构建越脆弱。
- 决策：M0 用 `AppContainer`（`EropicApplication.container` 懒加载）手写装配；`EropicViewModel.factory(container)` 注入；不引入 Hilt / hilt-work / hilt-navigation-compose。
- 理由：编译更快、依赖图一眼可见、排错简单；M0 不存在需要多模块注入的场景。
- 后果：M1 引入 Worker、多 ViewModel、多 Repository 后，需要手动维护构造参数；届时评估是否迁移 Hilt（迁移成本主要在 ViewModel/Worker 工厂）。
- 备选：现在就上 Hilt（更规范，但要额外 KSP 处理器 + Worker 工厂，M0 收益低）。

## ADR-0008：设置用 DataStore + App 内收藏独立于 MediaStore + DB v2 显式迁移

- 状态：已采纳（2026-10-27）
- 背景：M1 需要主题/列数/默认排序/显示开关等偏好，需要"收藏"筛选；同时 v1 数据库已在用户手机上建立了 10 万级索引。
- 决策：
  - 偏好存储用 `androidx.datastore.preferences`（`SettingsRepository`，文件名 `eropic_settings`），字段封装为不可变 `AppSettings`，读取失败回退默认值；
  - 收藏拆两层：`MediaEntity.isFavorite` 映射 MediaStore 的 `IS_FAVORITE`（只读展示）；`MediaEntity.localFavorite` 存 App 自己写入的收藏，UI 判定为 `localFavorite || isFavorite`，**不写回 MediaStore**；
  - 数据库版本升到 v2，提供 `MIGRATION_1_2`（`ALTER TABLE media_item ADD COLUMN localFavorite INTEGER NOT NULL DEFAULT 0` + `CREATE INDEX index_media_item_relativePath`），保留 `fallbackToDestructiveMigration()` 仅作未来遗漏迁移的兜底。
- 理由：写 MediaStore 收藏需要额外权限/系统"收藏"语义不一致，App 内收藏不惊动系统库；显式迁移避免升级即重扫 10 万张（几分钟到几十分钟）。
- 后果：App 内收藏与系统相册收藏不同步（卸载即丢失，需在关于页说明）；今后每次改表都必须补迁移，否则用户索引被清空。
- 备选：收藏写回 MediaStore（权限/兼容性风险）；设置用 SharedPreferences（无 Flow、异步易错）；每次升级清库重建（用户体验不可接受）。

## ADR-0009：缩略图用自建磁盘 LRU 缓存（320px WebP，cacheDir）

- 状态：已采纳（2026-10-28）
- 背景：Coil 的磁盘缓存不缓存 `content://` 本地文件，网格直接解原图（3~10MB → 几十 MB 位图），十万张滚动必然掉帧、易触发内存压力；用户明确不希望"为了浏览在后台一直跑任务"。
- 决策：
  - 自建 `ThumbnailCache`：解码一次长边 320 → WebP（质量 80）落到 `cacheDir/thumbs/<分片>/<key>.webp`；
  - key 含 `id + sizeBytes + dateModifiedMs`，图片被编辑/替换后自然失效，无需额外失效逻辑；
  - 三级来源：① 索引阶段已有 320 解码，顺手写缩略图（不额外解码）；② 网格滚动到未缓存项时按需生成（同一 key 用 Mutex 去重）；③ 可选"充电时补齐"WorkManager 一次性任务，默认不主动跑；
  - 上限默认 1GB，可配 512MB/1GB/2GB，超限按 lastModified 删到 80%；放 cacheDir 是因为系统清理/卸载可丢弃、不占图片空间、不会被相册扫到。
- 理由：浏览"即时性"不能依赖后台常驻；把一次解码的产物复用给指纹与缩略图，是这套流程里最省电的选择。
- 后果：索引时间增加约 10~20%；100k 张约占 1.2~1.8GB 缓存；关闭缓存后网格退回原图（可用的降级路径）。
- 备选：Coil 自定义 Fetcher 解原图（内存峰值不可控）；预生成全部缩略图（首次极慢且占空间）；用系统 `MediaStore.Images.Thumbnails`（Android 10+ 已废弃且不可靠）。

## ADR-0010：自动同步 = 进程内 ContentObserver（防抖 1.5s）+ WorkManager 周期 12h 兜底

- 状态：已采纳（2026-10-28）
- 背景：用户拍照/删图后希望图库立刻正确，但不接受后台常驻服务。
- 决策：
  - `MediaChangeObserver` 监听 `MediaStore.Images.Media.EXTERNAL_CONTENT_URI`（`notifyForDescendants=true`），主线程只做防抖提交，1.5s 内的连发合并成一次；
  - 触发后走 `SyncScheduler.requestImmediate`（唯一一次性任务，REPLACE）→ `SyncWorker` 调 `MediaRepository.syncFromMediaStore` 全表对账；
  - `ensurePeriodic` 以 12h + `KEEP` 兜底进程被回收期间的变化；
  - 无读取权限时直接 `success()` 不重试（权限只会由用户操作改变，retry 白耗电）；Android 14 仅部分授权也照常同步（`scanned == 0` 不会清库）。
- 理由：观察者保证"进程活着就准"，周期任务保证"进程死了也会补"；把任务交给 WorkManager 而不是内存协程，退后台不会半途被掐。
- 后果：每次触发是全表对账（10 万张几秒~几十秒），持续变化时可能每隔几秒跑一次；后台**不算指纹**（省电），新图的重复分组要等用户手动索引。
- 备选：App 内常驻 ForegroundService（耗电、通知栏常驻，违背用户偏好）；只在启动时扫一次（图库会过期）；纯周期无观察者（拍照后要等 12h）。

## ADR-0011：M2 清理页 = 分类入口 + 只读检索（不做自动删除）

- 状态：已采纳（2026-10-28）
- 背景：M2 要交付"重复/相似/大文件/久远/截图/模糊"的检索能力，但写权限（移动/回收站）要到 M3 才落；如果清理页一开始就带删除按钮，等于把未验证的文件操作暴露给 12 万张真实照片。
- 决策：
  - 清理页用 6 个分类 chip 平铺（`CleanupCategory`），前两个读查重分组表（EXACT/NEAR），后四个读检测器；内容用 `produceState` 按（分类, 刷新计数, 分组变化）重算；
  - 检测器全部只读、只返回 `MediaEntity` 列表 + 统计（命中数/可释放字节），不写库、不碰文件；
  - 对比预览（`CompareScreen`）双栏各自翻页、点图切下一张、两栏可看同一张做 1:1 对照；直接解原图（对比要看细节，缩略图不够）；
  - 所有写操作入口（批量移入回收站、真实移动、选择保留）在本期显示为 disabled，M3 接 `TrashRepository` / `FileOps` 后再启用；
  - 组合筛选 `MediaFilter` 是纯数据 + 纯 SQL 构造（`MediaFilterSql`），不依赖 UI，便于单测与后续 DSL（B-19）。
- 理由：检索能力（找得准）与写能力（动得了）风险量级不同；先把检索做扎实，写操作单独一版带回收站与二次确认，符合"删除决策交给用户"的产品红线。
- 后果：清理页暂时只能"看"，用户要清理还得等 M3；截图/模糊是启发式，必然有误判，UI 只给"疑似"措辞。
- 备选：M2 就接回收站（风险前置，权限路线还没真机验证）；只做重复不做检测器（大文件/久远其实是最快见效的清理维度）。
- 后续（M3，2026-10-28）：写入口已按 ADR-0012/ADR-0013 全部启用，清理页仍是"用户逐组确认"，不做自动删除。

## ADR-0012：侧载分发 → 直接申请 MANAGE_EXTERNAL_STORAGE（不走 MediaStore 请求式）

- 状态：已采纳（2026-10-28）
- 背景：M3 要做"真实移动文件 + 回收站（同卷秒级 rename）"。MediaStore 的写操作 API（`createWriteRequest` / `createTrashRequest`）每次都要弹系统确认框，批量清 500 张要弹几十次；而 Play 的 All-files-access 政策只约束上架应用。本项目**不上架、GitHub 开源、侧载安装**（用户已确认），可由用户自己决定授予"所有文件访问"。
- 决策：
  - Manifest 声明 `MANAGE_EXTERNAL_STORAGE`（附 `tools:ignore="ScopedStorage"` + 注释指向本 ADR）；
  - 应用内用 `StorageAccess.requestIntent()` 跳 `ACTION_MANAGE_APP_ALL_FILES_ACCESS_PERMISSION`（带 package uri，失败回退全局列表页）引导用户授权；
  - **权限是可选增强**：未授予时读取/查重/预览完全正常，真实移动、移入回收站、恢复、彻底删除入口统一置灰并提示原因；
  - 文件操作用 `java.io.File`（`renameTo` 优先，失败回退"复制 + 删源"），不依赖 SAF/MediaStore 逐次确认；
  - 每次写操作后调 `MediaScannerConnection.scanFile` 修正系统索引，Room 同步更新。
- 理由：侧载场景下这是唯一能支撑"批量、秒级、无系统弹窗"的真实文件操作路径；同时保留"不授权也能用"的只读体验，风险可控。
- 后果：`MANAGE_EXTERNAL_STORAGE` 属于高风险权限，若未来上架 Play 必须改回 MediaStore 请求式或 SAF（需重写 `FileOps`/回收站层）；国产 ROM 对该权限的引导页路径不一（部分需在"特殊应用权限"里找）。
- 备选（未采纳）：① MediaStore `createWriteRequest`（≤2000 URI/次，逐次系统弹窗，批量体验差）；② 纯 SAF（`DocumentFile` 每文件一次 IPC，10 万级不可行）；③ 只做账号内"逻辑删除"（违背用户"移动真实存储位置"的需求）。

## ADR-0013：回收站 = 同卷 rename 到 `.EropicTrash` + `trash_item` 表 + Snackbar 撤销

- 状态：已采纳（2026-10-28）
- 背景：用户要求"不许自动删、删除先进回收目录、默认 30 天、一键恢复"。系统 `IS_TRASHED`（API 30+）只能作用于本应用自己插入的条目，或需要 `MANAGE_MEDIA`；且系统"最近删除"的保留策略由 MediaProvider 决定，App 里看不到全部、也不可控。
- 决策：
  - `TrashRepository.moveToTrash`：同卷 `rename` 到 `<volume>/.EropicTrash/`（毫秒级、零拷贝），写入 `.nomedia` 防止被相册扫到；跨卷才走"复制 + 删源"；
  - 每项落库 `trash_item`（mediaId/displayName/trashPath/originalPath/sizeBytes/mimeType/trashedAtMs/expiresAtMs），并删除 `media_item` 中该行、扫描旧路径修正系统索引；
  - 恢复：rename 回 `originalPath`，重名自动加 `(1)`，然后扫描新路径；彻底删除/清空：直接删文件；
  - 所有写操作落 `operation_log`（TRASH/RESTORE/MOVE/DELETE/EMPTY_TRASH + payload），为后续"操作历史/撤销"留口子；
  - 保留期 30 天（`RETENTION_DAYS = 30`），启动时 `cleanupExpired()` 清理过期项；删除后 Snackbar 提供 5 秒"撤销"（调 `restore`）。
- 理由：同卷改名是手机上最快的"移动"，既满足"不做逻辑删除"（文件真的不在原目录了），又能在 30 天内无损恢复；自建目录让保留期、容量统计、UI 完全可控（延续 ADR-0004）。
- 后果：卸载 App 前必须提醒用户清空回收站，否则 `.EropicTrash` 会残留占空间；用户手动在文件管理器里改这个目录会破坏索引（恢复失败但文件仍在）；跨卷/外置存储只能复制。
- 备选：系统 `createTrashRequest`（保留期不可控、无 `MANAGE_MEDIA` 时不可用）；直接 `delete`（违背"避免误删"红线）。

## ADR-0014：批处理控制器 + 统一结果报告（C-06 / C-07）

- 状态：已采纳（2026-10-28）
- 背景：M3 的移动/清空回收站是"逐个串行 + 结束后一句 Snackbar"，用户看不到进度、无法暂停/取消；失败项只有计数没有原因（文件名/异常）。M4 要做复制、批量重命名、批量移入回收站，如果每个仓库各写一套循环，进度与失败语义会分叉。
- 决策：
  - 新增 `BatchController`（`core/fileops/BatchController.kt`）：`begin(label,total)/gate()/step()/fail()/finish()/reset()` + `pause()/resume()/cancel()`，暴露 `StateFlow<BatchState>`（active/label/total/done/failed/currentName/paused/cancelled）。仓库在**每一项操作前** `if (!batch.gate()) break`——暂停时挂起在挂起点，取消时返回 false 让循环收尾。
  - 所有写仓库（`MoveRepository.moveTo`、`CopyRepository.copyTo`、`RenameRepository.renameBatch`、`TrashRepository` 的批量入口）接收可选 `batch: BatchController?`，为空时行为等同 M3（向后兼容）。
  - 统一结果模型 `FileOpReport(type,title,requested,succeeded,failed,cancelled,bytes,failures: List<OpFailure>,logId,items)`，`OpFailure(name,reason)` 记录"哪张、为什么失败"。
  - UI 侧：`ui/common/BatchProgressBar.kt` 常驻 Scaffold 内容顶部（`state.active=false` 时不占空间），显示进度、当前文件名、暂停/继续/取消；结束后一律跳 `ReportScreen`（成功/失败/取消/字节四个统计 + 失败逐条原因 + 直达操作历史）。
- 理由：进度与取消是"批量删 500 张"这种高危操作的必需品（用户随时能停手）；统一控制器让"暂停语义"只实现一次，避免某个仓库漏检查。结果报告把"什么成功了、什么没成功、为什么"讲清楚，符合"决策交给用户"的产品红线。
- 后果：批处理期间禁止并发发起第二个写操作（`begin` 覆盖状态即可，UI 上按钮 busy 禁用）；`BatchState` 是进程内状态，杀进程后进度丢失（已处理项已落库，历史里可查）。
- 备选：① 用 WorkManager 做进度/通知（重，且写操作需要前台交互，不适合批量重命名的实时预览）；② 每仓库各写进度（重复代码、语义漂移）。

## ADR-0015：撤销闭环 —— operation_log payload 升 v2

- 状态：已采纳（2026-10-28）
- 背景：M3 的 `operation_log` 只记了 type/summary 和"新的 id 数组"，够用于展示历史，但不足以撤销——撤销要知道"从哪搬到哪"才能搬回去。用户要求 C-08「撤销闭环」。
- 决策：
  - payload 升到 v2：`{"v":2,"items":[{"id":..,"name":..,"from":"..","to":".."}]}`，由 `core/fileops/OpModels.kt` 的 `OperationPayload.encode/decode` 统一处理；`decode` **兼容 M3 的纯 id JSONArray**（老日志仍可展示，只是无法撤销）。
  - `OperationHistoryRepository.undo(logId)` 按类型分派：MOVE/RENAME/COPY → 把 `item.to` 搬回/清理回 `item.from`；TRASH → 从 `trash_item` 恢复（走 `TrashRepository.restore`，保留期与冲突命名规则复用）；DELETE/EMPTY_TRASH → 不可撤销（文件已不存在），历史页置灰并说明原因。
  - 撤销成功后 `markUndone(logId)`，同一日志只能撤销一次；撤销本身也写一条日志（type 复用原类型，summary 前缀"撤销"）。
  - 搬回前检查目标是否已被占用（冲突加 `(1)`），并 `MediaScanner.scanFile` 修正系统索引。
- 理由：payload 带 from/to 是"可逆操作"的最小信息集；兼容旧格式避免 DB v3 的老用户日志变空白。只允许"一次撤销"是为了避免反复撤销/重做把目录搅乱。
- 后果：撤销依赖真实文件还在原路径（用户手动移动过就会失败，此时报"目标不存在"并保留历史记录）；跨卷撤销是复制 + 删源，大文件慢。
- 备选：① 只做"删除撤销"（不满足 C-08）；② 做完整 undo/redo 栈（超出个人工具范围）。

## ADR-0016：图库日期分组与捏合列数

- 状态：已采纳（2026-10-28）
- 背景：A-01 要求"按日期分组"，A-05 要求"捏合缩放列数"。Paging 3 的 `LazyPagingItems` 只给条目，不能直接插标题行；网格手势如果粗暴消费事件，会把列表的单指滚动一起吃掉（M1 已踩过 `detectTransformGestures` 抢事件导致列表滚不动的坑）。
- 决策：
  - 分组：先把 `PagingData<MediaEntity>` `map` 成 `GalleryRow.Photo`，再 `insertSeparators` 插入 `GalleryRow.Header`（**分隔项必须与条目同类型**，否则 `LazyPagingItems[index]` 取不回）。`GalleryDates.monthKey/monthLabel` 只依赖 `dateTakenMs` + 设备时区，纯 JVM 可单测。
  - 渲染：`GalleryGrid` 用 `items(count, key, span)`，Header 的 `span = GridItemSpan(maxLineSpan)` 占满整行；key 用 `header-<key>-<index>` / `photo-<id>` 保证稳定。
  - 捏合：`Modifier.pinchToChangeColumns` 用 `awaitEachGesture` + `awaitPointerEvent` **只观察不消费**（不调 `consume()`），双指时按累计 `calculateZoom()` 跨过 1.3 / 0.7 阈值调一档，单指时清零累计——滚动仍由 LazyVerticalGrid 自己处理。
  - 捏合结果只写 `columnOverride`（本次浏览有效），**不回写**设置；设置里的 `gridColumns` 是默认值，切换设置时用 `LaunchedEffect` 清掉 override。
- 理由：insertSeparators 是 Paging 官方给"分组标题"的唯一正路（在 Flow 层，UI 只负责 span）；手势"只读不写"是既拿到缩放又不破坏滚动的唯一低成本解法。
- 后果：分组只在按拍摄时间排序时生效（按大小/名称排序时强行插月份标题没有意义）；分组标题会增加 item 数量，10 万张按月份约 +1000 行，可忽略。
- 备选：① 在 UI 层边渲染边算标题（`LazyVerticalGrid` 拿不到前一项，容易错位）；② 用 `detectTransformGestures` + `nestedScroll` 接管手势（复杂且易回归）。
- v0.2 补充：用户要求"点击时间标题可折叠/展开该时间的图、可改按日"，分组开关从 `dateGrouping: Boolean` 升级为三档 `DateGroupMode { NONE, MONTH, DAY }`（`AppSettings.dateGroupMode`，`dateGrouping` 保留为派生只读属性以免旧代码编译失败）；折叠状态 `rememberSaveable` 保存折叠的 key 集合，`GalleryDisplayGrid` 负责 peek 组装与分页哨兵。

## ADR-0017：DB v4 + 搜索 / 存储总览 / 保存筛选

- 状态：已采纳（2026-10-28）
- 背景：M4 新增 A-11 搜索、E-01~E-04 存储总览、B-17 保存筛选。搜索要能在文件名/路径上模糊匹配；总览要按格式/年份/目录聚合；保存筛选要能把 `MediaFilter` 持久化。
- 决策：
  - `MediaFilter` 增 `nameLike`，`where()` 末尾追加 `(displayName LIKE ? ESCAPE '\\' OR relativePath LIKE ? ESCAPE '\\')`，与其它筛选条件是 AND 关系（`%`/`_` 转义复用 `escapeLike`）。
  - 聚合查询放 `MediaDao`：`statsByFormat()`（`mimeType`）、`statsByYear()`（`strftime('%Y', dateTakenMs/1000,'unixepoch','localtime')`）、`statsByFolder(limit)`（`relativePath`），统一投影到 `StatRow(@ColumnInfo(name = "groupKey") val key, itemCount, totalBytes)`。
  - **SQL 别名必须写 `AS groupKey`**：`KEY` 是 SQLite 关键字，写 `AS key` 会让 Room KSP 报 `mismatched input 'key' expecting {IDENTIFIER, STRING_LITERAL}`，并连带报 `Not sure how to convert a Cursor to this method's return type`。
  - 保存筛选：新表 `saved_filter`（id/name/filterJson/createdAtMs）+ `SavedFilterCodec`（`MediaFilter` ⇄ 只含非空字段的 JSON），DB `version = 4` + `MIGRATION_3_4`（`CREATE TABLE IF NOT EXISTS saved_filter`），`addMigrations(MIGRATION_1_2, MIGRATION_2_3, MIGRATION_3_4)`。
  - 搜索入口：`SearchScreen` 300ms 防抖 + `viewModel.filterCount/filterSumSize(MediaFilter(nameLike=query))` 显示命中数与体积，点击结果用 `searchIds(query)` 进查看器；空查询时展示已保存的筛选和常用目录。
- 理由：全部走 Room + 已有索引，不引入 FTS/搜索引擎（10 万级 `LIKE '%kw%'` 全表扫描在 WAL 下约几十毫秒，可接受）；JSON 存筛选让 `MediaFilter` 继续演进（新增字段旧记录仍可解码）。
- 后果：模糊搜索是前缀无关的全表扫描（`%kw%`），30 万张时会明显变慢——若后续变慢再上 FTS4/FTS5 虚表；`filterJson` 无 schema 版本号，将来字段语义变更需兼容处理。
- 备选：① Room FTS 虚表（分词对中文文件名不友好，且要维护同步触发器）；② 把筛选存进 DataStore（无法按名称排序/删除单条，不适合多条记录）。

## ADR-0018：增量同步按字段比对 + 差异删除 + 权限缺失保护

- 状态：已采纳（2026-10-28，审查后修复）
- 背景：初版的 `syncFromMediaStore` 用 `(id → dateModifiedMs)` 判变化，并且开头就 `markAllAbsent()` 再逐条 `markPresent()`。三个真实漏洞：① 系统相册里加星/改标题不改 `DATE_MODIFIED`，索引永远不更新；② Android 14「仅选择部分照片」授权下查询返回 0 行，会把整库标成缺席（图库瞬间变空）；③ `upsertAll`（REPLACE）会把已算好的 dhash/phash/收藏一起清掉，下次索引重算。
- 决策：
  - 比对字段扩到 `MediaIdState(displayName, relativePath, sizeBytes, isFavorite, dateModifiedMs)`；未变的行不写库，变了的走 `updateStoreFields(...)` **只更新 MediaStore 侧字段**（保留 `localFavorite`/指纹）。
  - 缺席判定改成差集：`stale = existing.keys - seenIds`，只 `markAbsent(stale)`；且仅当"有完整媒体权限"且（`scanned == 0` 或 `dropRatio >= 0.5`）才判为真删除，避免误清空。
  - API 31/32 补 `READ_EXTERNAL_STORAGE(maxSdkVersion=32)`（这两版没有 `READ_MEDIA_IMAGES`，缺了会永远停在授权页）；`MediaPermissions` 按系统版本选权限名。
  - 后台对账沿用设置里的扫描范围：`SyncWorker` 先读 `settingsRepository.current().scanScope()` 再同步，且 `runAttemptCount >= 3` 才 `Result.failure()`。
  - 索引任务取消时重新抛 `CancellationException`，不再被写成 ERROR。
- 后果：单批索引写入放进一个事务；同步逻辑比"全量重写"复杂，但避免了 10 万行索引被误清空与指纹重算。

## ADR-0019：保留期变更重算 + 写操作后重算重复分组

- 状态：已采纳（2026-10-28，审查后修复）
- 背景：① `trash_item.expiresAtMs` 在移入回收站时写死，用户后来把保留期从 30 天改成 7 天（或改成"永久保留"）时旧条目仍按原值到期，"永久保留"名不副实；② 移入回收站只删 `media_item`，不动 `duplicate_member`/`duplicate_group`，分组卡长期显示虚高的「N 张 · 可释放 X」；③ `DuplicateScanner` 只 `clearGroupsOfKind` 不 `clearMembersOfKind`，旧成员行成为孤儿，表只增不减。
- 决策：
  - `TrashDao.remarkRetention(days, maxExpiry)` + `TrashRepository.applyRetention(days)`：`days <= 0` 写 `Long.MAX_VALUE`（永久），否则 `trashedAtMs + days*86400000`；`ViewModel.setRetention` 先落设置、再重算、再申请清理。
  - 回收站移入成功后 `pruneDuplicateGroups(mediaIds)`：删成员行 → 按剩余成员重算 `memberCount/reclaimableBytes`（口径：保留体积最大的一张）→ 删成员不足 2 的组及成员行；失败不影响主流程。
  - 扫描两侧都先 `clearMembersOfKind` 再 `clearGroupsOfKind`（子查询依赖 group 行，顺序不能反）。
  - 回收站读写前检查卷是否挂载（`volumeAvailable`），未挂载只报「暂不可恢复/删除」，不删记录；写回收站记录失败时把文件 rename 回原处。
- 后果：分组统计与保留期永远自洽；代价是每次写操作多几条 SQL（毫秒级）。

## ADR-0020：目录大小写以文件系统为准（DATA 反推 + 首段校对）

- 状态：已采纳（2026-10-28，v0.2）
- 背景：用户实测发现 Eropic 的文件夹页同时出现 `Pictures` 和 `pictures`，某些图片的详情页显示 `/storage/emulated/0/pictures/...`，而系统文件管理器/MT 管理器里只有首字母大写的 `Pictures`。原因是 MediaStore 的 `RELATIVE_PATH` 由写入者给定，历史数据里存在小写变体，直接当真值就会"凭空多出目录"。
- 决策：
  - `MediaStoreDataSource` 优先用 `DATA`（绝对路径）反推 `relativePath`（`StoragePaths.relativePathOf`），`DATA` 缺失才回落 `RELATIVE_PATH`；两条路径都过一遍 `PathCase.canonicalize`：只把**首段目录名**按 `File.list(卷根)` 的实际文件名校正（`ConcurrentHashMap` 缓存 60s）。
  - 不做全段校验：深目录逐段 `list()` 在 10 万张规模下是灾难，且首段就能解决 99% 的"同一目录两个名字"。
  - 旧行不需要专门的迁移：`MediaIdState` 已含 `relativePath`，下一次增量同步会判定"变了"并 `updateStoreFields` 纠正。
- 后果：文件夹页与系统文件管理器一致；`DATA` 在 Android 10+ 已废弃但仍可读，属过渡手段，未来若彻底移除需改用 `RELATIVE_PATH` + 卷根 `list()` 逐段校正（暂不做）。
- 备选：① 直接用 `RELATIVE_PATH`（就是当前问题的成因）；② 全段路径校对（IO 次数随深度线性增长，不可接受）。

## ADR-0021：回收站位置可配置 + 入口从底部 tab 移到清理页

- 状态：已采纳（2026-10-28，v0.2）
- 背景：① 用户找不到回收站文件到底在哪，「默认卷根 .EropicTrash」对普通用户不可见（以 `.` 开头，系统相册/文件管理器默认隐藏）；② 底部导航已有 5 个 tab，后续还要加功能，用户明确要求"回收站按钮挪到清理界面，防止底部拥挤"。
- 决策：
  - 设置项 `trashRelativeDir`（DataStore，默认 `""` = 卷根 `.EropicTrash`）。`SettingsRepository.normalizeTrashDir` 统一：反斜杠转 `/`、去首尾 `/`、拒绝绝对路径与 `.`/`..`、末级不是 `.EropicTrash` 时自动补上（所以用户填 `Pictures` 也会变成 `Pictures/.EropicTrash`）。
  - `StoragePaths.trashDir(root, relativeDir)` 生成目录；`TrashRepository` 注入 `SettingsRepository`，每次移入时读取当前值。
  - 已有条目**留在原目录**照常可恢复/删除（`trash_item.trashPath` 是绝对路径，与设置无关）；页面上用 `trashLocations()` 列出所有出现过的回收站目录，`configuredTrashDir()` 显示"新图会去哪"。
  - 入口：清理页顶部并排两张入口卡（回收站 N 项 · X · 保留期 / 识图）；底部 tab 减为 4 个（图库/文件夹/清理/设置），回收站改为 `AppScreen.Trash` 全屏页。
- 后果：换目录后出现"多个回收站"，这是有意为之（迁移 100GB 文件既慢又危险）；清理页要说明清楚。
- 备选：① 换目录时搬移旧条目（跨卷复制 + 删除，几十 GB 时不可接受）；② 回收站固定卷根不给改（用户明确要求"给用户自主选择权"）。

## ADR-0022：识图 = 本地指纹检索 + 联网搜图（新增 INTERNET，仅用户主动触发）

- 状态：已采纳（2026-10-28，v0.2；**部分取代 ADR-0006 的"无网络权限"**）
- 背景：用户要求"选一张新图，在本地图库里按相似度找"，以及"联网识图"（参考 greasyfork 的 search-by-image 脚本与 FlutterPicOrigin）。前者纯本地可做（指纹已在库里），后者必须联网。
- 决策：
  - 本地：`ImageSearchRepository.findByMediaId/findByUri` 复用 `pagePresentItems` 分页 + 小顶堆 Top-N，`similarity = 100 * (1 - (0.6*dhash + 0.4*phash) / 64)`；可选 `keyword`（文件名/路径 LIKE）辅助过滤；源图没有指纹时现算一次。
  - 联网：`OnlineImageSearch`（OkHttp multipart，20s 超时、20MB 上限）实做 Google Lens / Yandex / Bing / ascii2d；TinEye/SauceNAO/IQDB/trace.moe 先返回"暂未支持"（要么要 API key，要么签名复杂）。
  - 权限：Manifest 加 `INTERNET`；只在用户点"联网搜图"那一刻把**用户选中的那一张**上传，不批量、不后台、不自动。
  - 关于页与设置页文案同步改成"仅「联网搜图」时联网"，不再宣称"没有网络权限"。
- 后果：曾经"物理上不可能联网"的强保证降级为"代码里只有这一处联网"+ 文档约束；若将来要恢复零联网，需删 `OnlineImageSearch` 与 `INTERNET`。
- 备选：① 完全不做联网识图（用户明确要求）；② 只做"用系统浏览器打开 Google Lens 上传页"（无法把本地图片直接带过去，体验差）。

## ADR-0023：质量综合评分自动选差图（多因子加权 + 可解释理由）

- 状态：已采纳（2026-10-28，v0.2）
- 背景：用户要求"自动全选质量差的那一张，比较要综合多角度：总像素、格式（有损/无损）、bpp（每像素比特）、创建时间（越新越好）、文件名是否更完善"，并要求"左一张右一张，每张边上写参数比较，并标记出做出选择的依据"。
- 决策：
  - `QualityScorer.assess(members)` 对组内每张算 `QualityScore(total, factors)`，权重：总像素 0.45、格式 0.10、bpp 0.15、时间 0.08、文件名 0.05、清晰度 0.17。清晰度只在**全组成员都有** `blurScore` 时计入，否则把其余权重归一化——否则"没算过指纹的组"会系统性偏向某一张。
  - 输出 `GroupQualityAssessment(scores, keepMediaId, trashIds, rationale, confidence)`：`rationale` 是可直接展示的中文句子（"保留的这张像素是另一张的 2.4 倍"），`confidence = (分差/30).coerceIn(0,1)`。
  - UI：`QualityGroupCard` 顶部 A/B 双图并排，每张下面逐项列"参数名 / 值 / 得分"，底部"为什么这么选"；按钮文案明确"按建议移入回收站（N 张）"，仍走回收站（30 天内可恢复），**不自动删除**。
  - `KeepStrategy.BEST_QUALITY`（"按质量综合评分"）加入手动策略枚举，与"留最大/留最新"等并列。
- 后果：给了"一键按建议清理"的最短路径，同时每个判断都能追溯到具体参数；纯启发式（无 ML），极端情况（如无损 PNG 截图 vs 高像素噪点照片）可能与直觉不符，所以保留手动策略作为回退。
- 备选：① 只按文件体积（最省事，但"体积大"≠"质量好"）；② 训练/引入质量评估模型（体积与推理成本对 100 万级不现实）。

## ADR-0024：versionCode 用构建时间戳 + APK 名带构建时间 + 自定义图标

- 状态：已采纳（2026-10-28，v0.2）
- 背景：用户把新 APK 下载到手机后，系统仍提示"已安装/未更新"，必须手动改包名才能装上——因为 `versionCode` 固定为 1/2，同名 APK 又被浏览器当成同一个下载文件。同时应用还用的是 Android Studio 模板图标。
- 决策：
  - `versionCode = (构建毫秒 / 1000).toInt()`（秒级时间戳 ≈ 1.79e9，低于 2100000000 上限，且每次构建都更大 → 系统必然当作新版本覆盖安装）。
  - `BuildConfig.BUILD_TIME_MS / BUILD_STAMP` 由 `buildConfigField` 注入，关于页显示"构建时间"。
  - APK 文件名通过 `androidComponents.onVariants` 反射设置 `outputFileName` 为 `Eropic-<variant>-<versionName>-<yyyyMMdd-HHmm>.apk`（AGP 8.x 的 `VariantOutput` 没有公开 setter，只有实现类有；拿不到就静默跳过，不影响构建）。**不要**用 `Copy` 任务"另存一份"——Gradle 会报 "detected a problem with the following location"，因为任务同时读写同一输出目录。
  - 图标：自适应图标（`ic_launcher.xml` 的 background/foreground/monochrome 三层）自绘：深青渐变背景 + 两张叠放的照片卡 + 山形与太阳，monochrome 层供 Android 13+ 主题图标使用。
- 后果：每次构建 versionCode 都变，覆盖安装必定成功；代价是"同一版本号对应多个构建"（开发期可接受），发正式版时应改用固定递增的 versionCode。
- 备选：① 手动递增 `versionCode`（忘改就装不上，用户已踩过）；② 用 `adb install -r`（用户是浏览器下载安装，不适用）。

## ADR-0025：识图拆成「本地识图 / 联网识图」两块 + 服务商裁到 4 个 + SauceNAO Key 落 DataStore

- 状态：已采纳（2026-10-28，v0.3）
- 背景：v0.2 把本地相似图检索与联网以图搜图混在同一个页面、同一屏里，用户看不出这是两种完全不同的操作（一个不出本机、一个要把图上传到第三方）；同时列了 8 个服务商，其中 Bing/TinEye/IQDB/trace.moe 在手机上要么需要登录、要么反爬严重、要么基本没人用来查照片，属于噪音。
- 决策：
  - 页面拆两段：**本地识图**（复用已有 dHash/pHash 指纹，在整个图库找相似图，可加文件名关键词辅助）与**联网识图**（把当前选中/拍摄的这一张上传到用户点选的服务商，打开浏览器看结果）。
  - 服务商只留 4 个：`GOOGLE_LENS`、`YANDEX`、`SAUCENAO`、`ASCII2D`。前三家覆盖「通用照片 / 以图搜图 / 二次元插画」，ascii2d 补二次元与推特来源。
  - **API Key 只有 SauceNAO 需要**：它的官方 API（`POST https://saucenao.com/search.php`，multipart `api_key` + `output_type=2` + `file`）强制带 key，免费注册即得，按 `header.status` 区分成功(0)/无效 key(-1)/限流(-2)/搜索失败(-3)。其余三家走的是它们网页端的公开上传接口（Google Lens 的 `v3/upload`、Yandex 的 `images/search` 上传接口、ascii2d 的 `search.php` POST），**不需要 key**，但属于非官方接口，随时可能失效——所以每次失败都要把原因原样回显给用户，不能静默。
  - Key 存 DataStore（`Keys.SAUCE_NAO_API_KEY`，写前 `trim()`），设置页「联网识图」卡提供输入框 + 打开 saucenao.com 的按钮；未配置时识图页只提示「去设置填」，不阻止其他三家使用。
  - `OnlineImageSearch` 的构造函数接收 `sauceNaoApiKey: () -> String` 而不是字符串，这样改 key 不需要重建 ViewModel（v0.2 是直接传 value，改 key 后要重启 App 才生效）。
- 理由：拆两块解决「不知道会不会上传」的顾虑；裁服务商减少失败面；key 用 lambda 读是「配置热更新」的最小成本实现。
- 后果：SauceNAO 不填 key 就用不了（页面会说明）；三家网页接口失效时只能靠提示让用户换一家；上传是**用户点按才发生**，不做任何后台联网。
- 备选：① 全部走官方 API（Google/Yandex 没有开放的反向图搜 API，做不到）；② 只留 Google Lens（二次元图基本查不出来）。

## ADR-0026：清理页「小图」下线、换成「大图」——大图按分辨率，大文件按体积

- 状态：已采纳（2026-10-28，v0.3）
- 背景：原「小图」分类（< 200×200）在实际 10 万张图库里命中很少，且小图通常不是空间问题；用户明确说「清理的按钮小图不要，换成找大图」。
- 决策：
  - 新增 `LargeImageDetector`：按 `width * height >= 8_000_000`（800 万像素）从大到小取前 500 张（`DetectionDao.largeImages`），并提供不受 LIMIT 影响的 `largeImageSummary` 供清理报告统计。
  - 清理页分类 chip「小图」移除，换成「大图」；`SmallImageDetector` 类保留（随时可恢复入口），但 UI 不再暴露。
  - 「大文件」（按 `sizeBytes`）与「大图」（按像素）**并存不合并**：12MP 的 PNG 截图可能只有 800KB，8MP 的手机照片可能有 6MB，前者值得压缩/转存，后者只是普通照片，两类用户意图不同。
- 理由：分辨率是「这张图很占画面/值得单独处理」的稳定信号；体积已经被「大文件」覆盖。
- 后果：8MP 阈值写死在 detector 的 companion 里（`DEFAULT_MIN_PIXELS`），暂不开放设置；低于 8MP 的老照片不会出现在「大图」里。
- 备选：按「长边像素」排序（长截图会霸榜，不能代表「大图」）；按 DPI/文件体积混排（语义混乱）。

## ADR-0027：清理页改为「勾选式批量删除」，去掉「手动选择保留」策略对话框

- 状态：已采纳（2026-10-28，v0.3）
- 背景：v0.2 的清理分组卡把「自动建议」做得太隐晦——用户看不出系统到底选了哪一张，只看到左下角一行小字；而「手动选择保留」又要求用户在 2~4 张图里点单选再确认，操作成本比直接勾选还高，用户原话是「功能有点莫名其妙」。
- 决策：
  - 每组两张图并排（A/B），**每张缩略图右上角一个 Checkbox**，默认勾选 = `QualityScorer` 建议移入回收站的那些（`assessment.trashIds`），用户可逐个切换。
  - 每张图下面直接列 `QualityFactor`（像素 / 格式 / bpp / 时间 / 文件名 / 清晰度）的数值与得分，组底部显示 `rationale`（「做出选择的依据」）与综合分/置信度——**决策依据要能看见，而不是藏在文案里**。
  - 组内两个按钮：「全选建议（N 张）」与「移入回收站（M 张）」；列表顶部一条汇总条：「已选 N 张」+「全部按建议勾选」+「移入回收站」。
  - 删掉 `KeepStrategyDialog` 在清理页的入口（`KeepStrategy`/`KeepSuggester` 代码保留，`BEST_QUALITY` 仍在，避免历史调用点断裂）。
  - 删除仍走 `TrashRepository.moveToTrash`（回收站 30 天可恢复）+ `FileOpReport` 结果页，不新增任何「直接删除」路径。
- 理由：勾选态是用户能立刻理解的「我现在要删这几张」；一张图一行参数把「为什么选它」从黑盒变成白盒。
- 后果：清理页从「分组卡片列表」变成「带勾选的对比列表」，空间更紧凑；勾选状态只存在页面（离开页面即丢弃），不进数据库。
- 备选：保留策略对话框 + 在其上方显示建议（用户已明确否定）；一次只处理一组（10 万张图库处理不完）。

## ADR-0028：联网识图扩到 6 家 —— 百度识图（免登录）+ whos.tv（账号制）

- 状态：已采纳（2026-10-28，v0.4）
- 背景：用户要求补「百度识图」与「whostv」两个按钮，并先调研四个开源实现（ccloli/Search-By-Image、koishijs/plugin-image-search、4evergr8/FlutterPicOrigin、lolishinshi/imsearch）与 whostv-toolkit-manager。
- 调研结论（决定实现方式）：
  - **SauceNAO 官方 API 必须 key**。koishijs 的 `saucenao.ts` 不带 key 是因为它传的是**公网图片 URL**（`params.url`），由服务端去抓；我们的图在本机，没有公网 URL，只能 multipart 上传 ⇒ 保留「必须填 key」（延续 ADR-0025）。
  - ccloli/Search-By-Image（greasyfork 2998）与 FlutterPicOrigin 都靠「先传公共图床换 URL」来喂那些不支持上传的站（TinEye / IQDB / trace.moe）；公共图床会泄漏图片、且随时失效 ⇒ 不做。
  - whos.tv 是**非匿名**服务：`POST /api/login`（JSON username/password）→ cookie；搜图扣积分；`POST /upload-search`（multipart `file`）→ `/search-wait/<id>`；轮询 `GET /search-status/<id>`（带 `X-Requested-With: XMLHttpRequest`）→ 结果页 URL 或 `{"code":404000}`；成功码 200000。站点在 Cloudflare 后，官方客户端靠 curl_cffi/playwright 过挑战。
- 决策：
  - `ReverseImageProvider` 扩到 6 家：GOOGLE_LENS / YANDEX / SAUCENAO / ASCII2D / **BAIDU** / **WHOSTV**。
  - 百度识图：`POST https://graph.baidu.com/upload?uptime=<ms>`，multipart 字段 `image` + `image_source=PC_UPLOAD_SEARCH_FILE` + `range`，`Referer: https://graph.baidu.com/`，从响应 `data.url` 取 `graph.baidu.com/s?...` 结果页。国内可直连、免登录。
  - whos.tv：登录 → 上传 → 每 2s 轮询（最多 60s）；账号密码存 DataStore（`whos_tv_username`/`whos_tv_password`，只在本机、不上传），未配置时按钮提示去填而不是发请求。
  - Cookie 用**内存 CookieJar**（`ConcurrentHashMap<String, MutableList<Cookie>>`，按 host 分组，进程退出即失），不落盘：whos.tv 的会话 cookie 属于敏感凭据，没必要持久化。
  - 所有网络请求仍只由用户点按钮触发（延续 ADR-0022），无后台联网。
- 理由：百度识图是唯一「免登录 + 国内直连 + 上传接口」的可用服务，性价比最高；whos.tv 能补「截图找番号」这个真实场景，但必须由用户自带账号，我们只做通道。
- 后果：新增两个网络域（graph.baidu.com、whos.tv）；whos.tv 有 Cloudflare 挑战，可能返回 403 而失败（已在 UI 文案与错误映射里说明「需要账号/可能被 CF 拦」）；whos.tv 每次搜索消耗用户积分。
- 备选：给 whos.tv 内置公共账号（违反其条款且会耗尽积分，否决）；用公共图床换取 TinEye/IQDB（泄漏图片，否决）。

## ADR-0029：设置页统一「大框分组」+ 捏合列数扩到搜索/识图

- 状态：已采纳（2026-10-28，v0.4）
- 背景：用户反馈「设置里每个功能外面再加大框」（原来只有分组标题 + 直接铺卡片，区块感弱）；同时希望「图片显示界面加每行几个的放大缩小」——此前只有图库/文件夹网格支持捏合。
- 决策：
  - 新增 `SettingsSection(title, subtitle, content)`：`Card(fillMaxWidth)` + `surfaceContainerLow` + `elevation 0`，内部「标题/副标题 → HorizontalDivider → 内容」，**组内不再放卡片**（避免卡中卡）。设置页 9 个分组全部改用它。
  - 捏合列数从「图库/文件夹网格」扩展到**搜索页**（3~8 列）与**识图结果页**（2~8 列）：同一个 `Modifier.pinchToChangeColumns(columns, min, max, onChange)` 实现，捏合只改页面内的 `columnOverride`，不回写设置（避免误触改全局默认）。
  - 识图关键词过滤的语法在输入框下用 `bodySmall` 写明：同时匹配文件名与目录、不区分大小写、子串匹配、空格算关键词一部分、`%`/`_` 是普通字符（对应 `SimilarityMath.matchesKeyword` 的纯 Kotlin `contains` 实现，不走 SQL LIKE）。
- 理由：分组大框让「一个功能一块」在视觉上闭合；捏合是手机相册的通用手势，用户不需要找菜单。
- 后果：`SettingsScreen.kt` 从 744 行涨到 838 行，但结构更平（不再有 8 个独立 `*Card` 组件包裹）；捏合列数只影响当前页面会话。
- 备选：用 `LazyColumn` 的 sticky header（滚动时标题乱跳，且不如大框直观）；捏合直接写 `settings.gridColumns`（一页捏合污染所有页面，否决）。

## ADR-0030：文件夹级真实操作（重命名 / 删除 / 置顶 / 封面）

- 状态：已采纳（2026-10-28，v0.5）
- 背景：v0.5 之前文件夹页只是「只读聚合视图」，用户要求「文件夹右键应该有一些功能，比如重命名，更换图集封面，顶置，删除，选择」。这些是**真实文件系统操作**（重命名要改目录名、删除要把目录里所有图移进回收站），不能只在数据库里改。
- 决策：
  - 新增 `core/folders/FolderRepository.kt`：`renameFolder(relativePath, newName)`、`trashFolder(relativePath)`、`setPinned`、`setCover`、`defaultCover`，统一返回 `FolderOpResult(ok, message, changed, failures)`。
  - 重命名：`File.renameTo`（同卷，O(1)）→ 逐行 `MediaDao.updatePathAndName` 修正 path/displayName/relativePath → `SettingsRepository.renameFolderPrefs(old, new)` 迁移置顶与封面偏好（前缀匹配）→ `MediaScanner.scan` 扫新旧目录让 MediaStore 重新收录。名字校验复用 `RenameTemplate.validateName`（拒绝 `/\\:*?"<>|` 与 >128 字）。
  - 删除目录：`idsUnderFolder` 取该目录（含子目录）全部已索引图片 → `TrashRepository.moveToTrash` 逐张移入回收站（**不直接删文件**）→ 只删除变空的那几层目录 → 报告「还有 N 个未索引文件，因为不在索引里没有处理」。
  - 置顶与封面是**纯 App 内偏好**，存 DataStore（`pinned_folders`、`folder_covers`，后者按 `路径|mediaId` 逐行存），不写回文件系统，也不改 MediaStore。
  - UI 入口两处：列表行尾部 `⋮`、网格卡片长按，统一打开 `FolderActionsSheet`（打开 / 选择 / 重命名 / 更换封面 / 置顶 / 删除 / 包含子文件夹）。
- 理由：用户明确要「实际存储位置」的移动（v0.1 需求），文件夹重命名如果只改数据库，MT 管理器里名字不变，属于是假的。
- 后果：重命名后如果有图片正被查看器打开，URI 会失效（查看器会提示无法读取）；置顶/封面在换手机或清数据后丢失（不做备份导出）。
- 备选：用 SAF `DocumentsContract.renameDocument`（Android 11+ 对 Pictures 顶级目录之外的目录受限，且 10 万张级的递归重写仍需自己走，收益低，否决）；目录删除用 `File.deleteRecursively`（绕过回收站，违反「不允许自动删除」，否决）。

## ADR-0031：五个 Tab 统一 `EropicTopBar`，副标题占位保证等高

- 状态：已采纳（2026-10-28，v0.5）
- 背景：用户反馈「把图库文件夹清理识图设置顶部大小统一一下」——此前各页各写 `TopAppBar`，有的两行标题（标题 + 副标题）、有的一行，切换 Tab 时标题区高度跳动。
- 决策：
  - 新增 `ui/common/EropicTopBar(title, subtitle, onBack, actions)`：`titleLarge` 标题 + `bodySmall` 副标题；**副标题为空时也占位**（`height(16.dp)` 的空白 Text），从而五个 Tab 顶栏高度恒定。
  - 图库 / 文件夹 / 清理 / 识图 / 设置、以及二级页（搜索、存储总览、清理报告、历史、文件夹管理、关于、更换封面、筛选结果）全部改用同一个组件；需要返回箭头时传入 `onBack`。
- 理由：高度一致比「每页各调各的」更稳，也不会因为副标题有无而让内容区上下滑一下。
- 后果：副标题内容必须简短（一行），过长会被 `maxLines=1 + ellipsis` 截断；各页不再能自定义标题排版（有特殊需求的页面自己在外层包 Column）。
- 备选：用 `CenterAlignedTopAppBar` 统一（和左右动作按钮的视觉重心不符，否决）；不占位、靠 `Modifier.heightIn` 兜底（不同 Tab 仍会差几 dp，否决）。

## ADR-0032：本地识图关键词语法（空格 AND / 竖线 OR / 减号排除）

- 状态：已采纳（2026-10-28，v0.5）
- 背景：用户问「本地识图的语法写齐了吗，那如果是多关键词怎么处理」。v0.4 时只是「整串当子串」匹配，多关键词等于找不到。
- 决策：
  - 新增 `core/search/SearchModels.kt` 内的 `internal object KeywordSyntax`：`parse(raw)` 把输入切成 `Query(includes: List<List<String>>, excludes: List<String>)`——空白（含全角空格）分词，`|` 把同一组内的备选串起来（OR），前缀 `-` 表示排除，其余为必须同时命中的组（AND），全部转小写。
  - `matches(displayName, relativePath, query)`：每个 AND 组至少有一个 OR 备选命中、且没有任何排除词命中，即算命中；匹配对象是**文件名或目录相对路径**（任一命中即可），子串匹配、不区分大小写，`%` 与 `_` 按普通字符处理（纯 Kotlin `contains`，不走 SQL LIKE）。
  - `SimilarityMath.matchesKeyword` 委托给它，保证「指纹相似度筛选」与「关键词筛选」用同一套语义。
  - UI 在识图页关键词框下用 `bodySmall` 逐条写明语法（含示例「猫|狗」「-截图」「输入 cat 会命中 vacation.jpg」）。
- 理由：相册里最常见的是「按人名或地名过滤」，用户天然会想「猫 狗 都要」「只要截图」「不要截图」；用 grep 式语法不需要额外的筛选面板。
- 后果：关键词不能含空格（空格是分隔符），也不能搜索以 `-` 开头的名字（会被当排除词）；引号无特殊含义（不做词组匹配）。
- 备选：做成分段 chips 输入（手机上输入成本高，否决）；支持 SQL LIKE 通配（用户写 `%` 会变成通配符，反直觉，否决）。

## ADR-0033：联网识图协议改照抄 PicImageSearch，whos.tv 下线、IQDB 顶上

- 状态：已采纳（2026-10-28，v0.5）；部分取代 ADR-0028
- 背景：用户要求「去掉 whostv 的东西吧。然后搜图改成使用下面这个链接的方法 https://github.com/kitUIN/PicImageSearch/」。whos.tv 需要账号、扣积分、还在 Cloudflare 后面，实测价值低于维护成本。
- 决策：
  - `ReverseImageProvider` 六家固定顺序：GOOGLE_LENS / YANDEX / BAIDU / SAUCENAO / ASCII2D / **IQDB**（WHOSTV 连同账号密码设置项、CookieJar、轮询逻辑全部删除）。
  - 每个 provider 的端点、表单字段、参数都按 `kitUIN/PicImageSearch` 的 `engines/<name>.py` 逐行照抄，函数头注明对照文件：Lens `POST v3/upload` + `encoded_image`（**不能带 hl，会 403**）；Yandex `POST /images/search?rpt=imageview&cbir_page=sites` + `prg=1` + `upfile`；百度 `POST graph.baidu.com/upload` + `image` + `from=pc`；SauceNAO 官方 API（key 必填，延续 ADR-0025）；ascii2d `POST /search/file?type=color` + `file`，成功 302 到 `/search/color/<hash>`；IQDB `POST iqdb.org` + `file`。
  - 判定成功：Lens 从 HTML 里取 `a[href*="udm=37|44|48"]` 拼 `www.google.com`；Yandex 取重定向后的 URL；百度从 JSON `data.url` 取 `graph.baidu.com/s` 结果页；ascii2d 认 `/search/color|/search/bovw|uri=`；IQDB 认 URL 含 `iqdb.org`。
  - `OnlineImageSearch` 构造参数只剩 `(contentResolver, sauceNaoApiKey)`（不再有 whos.tv 账号回调），client 也不再挂 CookieJar。
- 理由：PicImageSearch 是这批站点里维护最活跃的 Python 实现，照抄它比照抄 2022 年停更的 greasyfork 脚本可靠；IQDB 与 ascii2d 同属二次元检索，但 IQDB 不需要 302 二次跳转，实现更干脆。
- 后果：仍是非官方网页接口，任何一家改版都会失效（每个函数头留了对照点，便于重新抓包修）；ascii2d / IQDB 需要代理；SauceNAO 必须用户自备 Key。
- 备选：TinEye（要先 POST 拿 `query_hash` 再 GET，两步会话）、Bing（`imageSignature` 需要 XOR 解密）、trace.moe / AnimeTrace（返回 JSON 识别结果而非结果页，UI 要另做一套）——都先不做。
- 教训（构建踩坑）：Kotlin 的块注释**可以嵌套**，KDoc 里写路径 `engines/*.py` 的 `/*` 会开一个嵌套注释，最终报 `Unclosed comment`；注释里提到 glob 要写成「engines 目录下的 *.py」这类不带 `/` 紧邻 `*` 的写法。

## ADR-0034：文件夹网格页只显示下一层文件夹，「包含子文件夹」收进页面菜单

- 状态：已采纳（2026-10-28，v0.5）
- 背景：用户要求「文件夹界面，网格状态下不要有本文件夹的图片那一块，就正常显示有几个文件夹就行，相册名字稍微大一点点。网格形态的顶部有点太大了，不需要，为什么包含子文件按钮不能点……把包含子文件夹按钮也放进菜单里，界面里就不要放了」。
- 决策：
  - 新增 `ui/folders/FolderGridScreen.kt`：网格只渲染**当前目录的下一层子文件夹卡片**（封面 + 名字 + 「N 张 · X」），不渲染本层图片、不渲染面包屑、不常驻「包含子文件夹」开关；卡片标题 `titleMedium`（比列表行的 `bodyLarge` 大一号）；置顶项排最前；点击卡片 = 下钻，长按 = 打开 `FolderActionsSheet`。
  - 「包含子文件夹」开关移到页面级三点菜单 `FolderPageMenu`（`FolderActionsSheet` 本身是 `ModalBottomSheet`，弹层里再弹层不可行），切换后的值作为进入详情页的**初值**。

  - 根目录的「包含子文件夹」在详情页仍禁用并说明原因（`relativePath` 为空时无法用 LIKE 前缀匹配，见 ADR/MediaQuery 注释），但网格页不再出现这个不可点的按钮。

- 后果：网格模式下要看某个文件夹里的照片，需要多点一步（进入详情页）；跨页共享的 `flattenVisible / orderPinnedFolders / FolderPageMenu` 等都定义在 `FoldersScreen.kt` 里用 `internal` 导出，两个文件存在耦合。
- 备选：网格卡片分「封面区 + 图片区」两段（就是用户要求删掉的那种，否决）；开关放顶栏做成图标（没有文字的开关看不懂，否决）。

## ADR-0035：搜索语法 v0.6——空格 = 同时包含、双引号 = 整段、减号 = 排除

- 状态：已采纳（2026-10-29，v0.6）；**部分取代 ADR-0032**（那次明确写了"关键词不能含空格、引号无特殊含义"，用户实测后反馈"现在的语法我没看懂"）
- 背景：用户要求「现在的语法我没看懂，要能支持空格分开，如果想要空格在一起就要用双引号框起来」。
- 决策：
  - 新增 `core/query/SearchText.kt`（公开 object）：`fun parse(raw: String?): Parsed` → `Parsed(groups: List<List<String>>, excludes: List<String>)`。手写扫描分词：双引号内的空格不切词、引号本身不进入内容；token 起始 `-` 标记为排除；全角空格也当分隔符；`|` 继续表示或（兼容旧写法）。
  - `KeywordSyntax`（识图页用的关键字筛选）改成直接委托 `SearchText.parse`，保证"搜索页"和"识图页"是同一套语义。
  - `MediaFilterSql.where()` 里 `nameLike` 不再当成一整串，而是解析后：每个 AND 词组生成 `(displayName LIKE ? OR relativePath LIKE ?)`，词组之间 AND；排除词生成 `(displayName NOT LIKE ? AND relativePath NOT LIKE ?)`。`MediaFilter` 没有新增字段，`SavedFilterCodec` 仍存用户原文。
- 理由：相册搜索的高频诉求是"人名 + 年份"这种组合，空格当 AND 最符合直觉；而"我的 照片"这类带空格的相册名必须能用双引号表达，否则搜索框无法表达用户真实意图。
- 后果：以 `-` 开头的文件名无法被搜索命中（会被当排除词）；引号不成对时按普通字符处理（不报错、不全量吞掉输入）。
- 备选：做成 chips 分段输入（手机上输入成本高，否决）；保留旧语法只改文案（用户明确说看不懂，否决）。

## ADR-0036：搜索历史用独立 DataStore（最多 50 条，可单条删除/一键清空）

- 状态：已采纳（2026-10-29，v0.6）

- 决策：
  - 新增 `core/search/SearchHistoryStore.kt`：**独立的** `preferencesDataStore(name = "eropic_search_history")`（不挤进 eropic_settings，历史写入频率高、体积可变）。`history: Flow<List<String>>`、`add(query)`（trim、空忽略、去重、最新在前、上限 50）、`remove(entry)`、`clear()`；存储格式是换行拼接的纯文本。

## ADR-0037：联网识图裁到 5 家——去 Yandex、SauceNAO key 内置、百度上传前缩放

- 状态：已采纳（2026-10-29，v0.6）；部分取代 ADR-0033（六家 → 五家）
- 背景：用户实测后提出三条：「saucenao 的 api 我写代码里了，所以设置里的联网识图的框删掉」「百度识图用不了，是不是要加什么 cookie」「yandex 去掉不要了」。
- 决策：
  - `ReverseImageProvider` 删除 YANDEX，剩 GOOGLE_LENS / BAIDU / SAUCENAO / ASCII2D / IQDB；`OnlineImageSearch` 里 Yandex 的端点、`rpt=imageview` 参数、302 结果页解析、正则、`yandexResultUrl` 全部删除。
  - SauceNAO key 从 `AppSettings`/设置页搬到 `OnlineImageSearch.SAUCE_NAO_API_KEY` 常量；`sauceNaoApiKey` 字段、DataStore key、setter、"去设置里重填"类文案全部移除；`OnlineImageSearch` 构造只剩 `(contentResolver)`。
  - 百度识图：**不需要 Cookie**，需要请求头 `Acs-Token: `（空值，缺了会回 `{"status":1,"msg":"Reject"}`）与 `Referer`。实测空图回 `status=1002 Params illegal`，约 5MB 以上连接被直接断开，因此上传前若「体积 > 4MB」或「不是 jpeg/png」就先缩到 1600 长边 JPEG（`shrinkForSauceNao` 泛化成 `shrinkForUpload(bytes, longEdge, thresholdBytes)`）。响应解析新增 `ReverseSearchParsers.baiduStatus` + `baiduStatusMessage` / `baiduHttpMessage`，把 status/HTTP 码翻成中文可执行提示（换一张、太频繁、太大）。
  - 设置页「联网识图」分组整段删除；识图入口只保留底栏 Tab 和清理页卡片。
- 理由：Yandex 结果页依赖 302、在国内还要代理，维护收益低；SauceNAO 的 key 本来就是用户提供的公共 key，做成设置项只会让用户以为"要自己申请"；百度失败的真正原因是图片过大而非缺 Cookie。
- 后果：SauceNAO 免费额度共享，用尽后提示"稍后再试"而不是让用户去换 key；Google Lens / SauceNAO / ascii2d / IQDB 仍需代理，百度识图国内直连可用。
- 备选：把 key 留在设置里但预填（用户仍会困惑，否决）；百度分支不缩放、只提示"图片太大"（可执行性差，否决）。

## ADR-0038：EropicTopBar 副标题为空时不再占 16dp

- 状态：已采纳（2026-10-29，v0.6）；**部分取代 ADR-0031**（"副标题恒占 16dp 保证换页时标题不跳"这个取舍被推翻）

## ADR-0040：指纹先写待落盘表 pending_signature，合并回主表时才刷新图库

- 状态：已采纳（2026-10-31，v0.7）；DB 版本 4 → 5
- 背景：用户反馈「索引进行时图库一直在闪，而且只剩最近两个月的图」「暂停/取消索引是不是白算了」。根因是指纹每算完一张就 `UPDATE media_item`，而图库的 Room `PagingSource` 观察 `media_item` 全表，于是每张图都触发一次分页失效与重新加载；再加上一屏只显示已加载的页，用户看到的就是"图库闪烁 + 只剩一小段"。
- 决策：
  - 新增表 `pending_signature`（`PendingSignatureEntity`：mediaId 主键、dhash、phash、blurScore、signatureVersion），MIGRATION_4_5 只建空表，不碰已有索引（用户不必重扫 10 万张）。
  - `MediaRepository.saveSignature()` 改为只写 `pending_signature`（hash_band 仍即时写，它不在图库的观察集里）；新增 `flushPendingSignatures()` 在**一个事务**里把待落盘行合并回 `media_item` 再清空，`countPendingSignatures()` 供进度展示。
  - 合并时机：每轮算完、取消、暂停、启动续算（`IndexCoordinator` 的 DONE/CANCELLED/PAUSED 分支与 `pause()`/`cancel()` 里都调）。
  - 顺带补上暂停/继续：`IndexCoordinator.pause()` / `resume()`（`IndexState.paused`），暂停时当前批跑完即落盘休眠，图库顶栏在 HASHING 阶段给「暂停 / 继续 / 取消」。
- 理由：把 N 次表失效压成 1 次，图库最多刷新一次；同时让"算到一半被打断"的成果真正落库，暂停不再是白算。
- 后果：`media_item.signatureVersion = 0` 的语义多了"结果可能还在 pending 表里"，因此自动续算判断要同时看 `countPendingSignatures()`；进程被系统强杀时最后一批未合并的指纹会丢，下次按未算过重算（最多一批）。
- 备选：给 PagingSource 加 distinct 过滤（治标，仍会整体重查）；把待落盘结果只放内存（暂停/取消就丢，用户明确问了"是不是白算"，否决）。

## ADR-0041：联网识图扩到 7 家，URL 型引擎统一走 1 小时临时图床

- 状态：已采纳（2026-10-31，v0.7）；部分取代 ADR-0037（5 家 → 7 家）
- 背景：用户实测「Google Lens 结果页打开是空的 / 不对」「加 onegai.moe 和 Lenso.ai」，并给了两个参考（greasyfork Search By Image、kitUIN/PicImageSearch）。
- 决策：
  - `ReverseImageProvider` 增加 ONEGAI、LENSO，固定顺序 GOOGLE_LENS / BAIDU / SAUCENAO / ASCII2D / IQDB / ONEGAI / LENSO；`OnlineSearchResult` 增加 `items: List<OnlineHit>`（title / similarity / extUrl / pageUrl / thumbnailUrl 全可空），UI 不再"成功后自动弹浏览器"，而是列结果行，由用户点开。
  - 新增 `core/search/ImageHost.kt`：把源图上传到 `litterbox.catbox.moe`（`time=1h`，1 小时后自动删除）换一个公网 URL。**选 litterbox 而不是 catbox 是因为会自动过期**，减少用户图片的长期外泄面。
  - ascii2d / IQDB / onegai / Lenso 统一走 `OnlineImageSearch.urlSearch(provider, bytes, mime, buildUrl)`：先上图床，失败则明确提示"该服务只接受公网图片链接，而临时图床上传失败了"，不再假装是网络问题。
  - **Google Lens 改 URL 模式优先**：`lens.google.com/uploadbyurl?url=<图床URL>`，图床上传失败才退回原 multipart 上传。原因：multipart POST 会 303 到 `lens.google.com/search?ep=...`，而该页面依赖**上传会话**，把 URL 交给系统浏览器打开时没有会话，用户看到的就是空白页——这正是用户反馈"Lens 不对"的根因。
  - ascii2d 的成功判定从"URL 含 uri=" 改为"URL 含 /search/color 或 /search/bovw 或 uri="，因为它的上传成功会 302 到 `/search/color/<hash>`，旧判定会把成功误报为失败。
- 理由：Lens / onegai / Lenso 只接受公网链接；用一次性图床比要求用户自己配图床现实得多，也比"直接告诉用户不支持"有用。
- 后果：这四个引擎需要网络代理（国内直连不可用）；临时图床不可用时这四家会整体失败（百度/SauceNAO 仍可直连）；上传源图会短暂离开设备，隐私说明已写进关于页。
- 备选：把图片 base64 塞进 URL（超过长度限制，否决）；在应用内自建图床（无服务器，否决）。

## ADR-0042：本地识图加"颜色画像精排 + 找同角色"，服务二次元图

- 状态：已采纳（2026-10-31，v0.7）
- 背景：用户要求「本地识图的算法还需要改进，重点是二次元图」以及「能不能识别角色」。
- 决策：
  - 新增 `core/search/VisualSimilarity.kt`：`ColorProfile(hueHistogram: IntArray(12), saturationMean, valueMean, edgeDensity, aspectRatio, isLikelyAnime)` 与 `profile(bitmap)` / `profileFromPixels(w,h,argb)` / `colorSimilarity(a,b)` / `combinedScore(dhashDist, phashDist, base, candidate)`。颜色相似度 = 色相直方图余弦 60% + 饱和度 15% + 明度 15% + 长宽比 10%；综合分：双方都像二次元时 `base*0.85 + color*0.15`，只有一方像则 −8（跨画风惩罚），长宽比误差 <5% +3。
  - `ImageSearchRepository` 在哈希粗筛（dHash ≤ maxDistance）后用	extbf{颜色画像精排前 60 条}：解码优先读 320px 缩略图，没有再看原图。只精排 Top-60 是因为解码是全流程最贵的操作，全库精排会把搜索变成分钟级。
  - 「找同角色」`findCharacterByMediaId / findCharacterByUri`（UI 侧别名 `findCharacterMatchesBy*`）：本地候选放宽到 120 条按综合分排序 + 联网依次问 SauceNAO、ascii2d，取第一个非空标题作为 `roleHint`（截 40 字），三档文案分别说明"识别为 X / 联网没给角色名 / 没联网"。
  - 空画像保护：`ColorProfile.aspectRatio <= 0` 视为无效，直接返回基础分——否则 `colorSimilarity` 会给空画像 40 分的默认值，把结果搅乱。
- 理由：dHash/pHash 只描述明暗结构，换配色（同角色不同画师、不同同人图）时汉明距离会很大；二次元图的色相分布比结构更稳定。
- 后果：识图多一次解码（Top-60），10 万库上约增加 1-2 秒；`isLikelyAnime` 是经验阈值，高饱和人像可能误判（只会让权重偏向颜色，不会改变候选集）；"找同角色"依赖联网，未联网时只给本地排序。
- 备选：上 CLIP/MobileCLIP 做语义向量（体积 + 首次算力成本，v1 明确不做，见规划文档）；纯颜色直方图（丢掉结构信息，同一配色不同角色会混，否决）。

## ADR-0043：应用内更新（GitHub Release 检查 + FileProvider 安装），版本比较用版本名

- 状态：已采纳（2026-10-31，v0.7）
- 背景：用户要求「给个 release 包能直接替换现有的包，app 内也要做更新检测」。
- 决策：
  - `core/update/UpdateChecker.kt`：`GET https://api.github.com/repos/33kurumi/Eropic/releases/latest`（UA=Eropic-Android-Updater），assets 里挑 `.apk` → `UpdateInfo(versionName, versionCode, notes, downloadUrl, pageUrl)`；HTTP 404 视为"仓库还没发 release"返回 null（不报错）；下载到 `cacheDir/updates/Eropic-<version>.apk`（先 `.part` 再 rename）。
  - **是否已是最新用版本名比较**（`VersionCompare.isNewer`：剥 `v` 前缀与 `-debug` 后缀、按数字段比较），**不用 versionCode**：本项目 versionCode 是构建时间戳（ADR-0024），本地新构建的包永远比线上 release 的时间戳大，比 versionCode 会永远显示"已是最新"。
  - 安装：`FileProvider`（`${applicationId}.fileprovider`，`res/xml/file_paths.xml` 只暴露 `cache-path updates/`）+ `ACTION_VIEW` + `FLAG_GRANT_READ_URI_PERMISSION`；Android 7+ 不允许 `file://`。
  - `app/build.gradle.kts`：`appVersionName = "0.7.0"`；release 增加 signingConfig——存在 `keystore/eropic-release.jks` 就用它（口令读 `eropic.storePassword` 等 gradle 属性或环境变量），不存在则回退 debug 签名，保证 `:app:assembleRelease` 在任何机器上都能跑通。
- 理由：侧载分发没有商店托管，更新检测只能自己查 GitHub Release；用 FileProvider 是 Android 官方唯一受支持的方式。
- 后果：正式签名需要用户自己生成 keystore 并保存口令（换签名必须卸载重装）；GitHub API 匿名限流 60 次/小时（本场景完全够用）；系统仍会要求用户为 Eropic 打开"安装未知应用"。
- 备选：内置下载器+静默安装（需要 root/系统签名，否决）；跳转浏览器下载（无法提示进度、装完还要手动找文件，否决）。

## ADR-0044：图库日期分组折叠用身份键，索引补暂停/继续

- 状态：已采纳（2026-10-31，v0.7）
- 背景：用户反馈「图库按日期分组时张数一直跳、折叠卡」与「指纹计算要能暂停」。
- 决策：
  - `GalleryDisplayGrid` 的 `remember` key 从 `itemSnapshotList`（`AbstractList` 逐元素 O(n) 比较，每次重组都扫一遍已加载项）换成 `SnapshotStamp(itemSnapshotList)`（用 `===` 身份比较重写 `equals/hashCode`）；同时保留 `loadedCount`、分组模式、日期排序、折叠集合作为 key。
  - 新增 `onVisibleGroupKeys: (Set<String>) -> Unit` 回报已加载的 Header 键，图库"显示方式"二级菜单据此提供「全部展开 / 全部收起」（不分组模式禁用）；「全部收起」用网格回报的真实键（非时间排序带 `#段号`），不自己拼日期。
  - 回调用 `rememberUpdatedState` 包一层，避免上层重组重启 Effect。
  - `IndexBanner` 扩为 `(indexState, onRetry, onPause, onResume, onCancel)`：HASHING 显示暂停/继续 + 进度，SYNCING/DEDUPING 显示取消，ERROR 显示重试；暂停文案明确"已算的结果已保存"。
- 理由：分组行数变化时列表会整体重排，若 key 依赖逐元素比较，每次重组都要 O(n) 且必然重算；用身份键在数据源未变时直接跳过。
- 后果：`itemSnapshotList` 若被 Paging 原地修改（同一 List 实例内容变化），身份键会漏掉更新——当前实现里 Paging 每次交付新快照，因此安全；"全部收起"只覆盖已加载分组（未加载的滚动到时是展开的）。
- 备选：把折叠态放进 ViewModel（要处理进程恢复与分页，收益不大，否决）；用 `LazyListState` 手工算可见范围（复杂且易错，否决）。

## ADR-0045：目录大小写以真实文件系统逐段校正（v0.8）

- 状态：已采纳（2026-10-31，v0.8）
- 背景：用户反馈「MT 管理器/系统文件管理器只有 `Pictures`，Eropic 里同时出现 `Pictures` 和 `pictures`」，且图片详情里的绝对路径指向 `pictures` 而真实路径是 `Pictures`。
- 根因：模拟存储是大小写不敏感文件系统。MediaStore 的 `DATA` 与 `RELATIVE_PATH` 都由写入方（MTP、第三方下载器、解压工具）提供，可能保留错误大小写；ADR-0020 当时只校对了首段目录，深层目录仍会分裂成两个相册。
- 决策：
  - `core/media/PathCase.canonicalizeDeep(relativePath, volumeRoot)`：逐段用真实目录名替换（`File(dir).list()` 结果按 `equals(ignoreCase = true)` 匹配），每级目录的 list 结果做 60 秒缓存，`MAX_DEPTH = 12` 保护；读不到目录时原样返回，幂等。
  - `MediaStoreDataSource` 的映射改为：`volumeRoot = StoragePaths.volumeRootOf(DATA) ?: primaryRoot()`；`rawRelative = StoragePaths.relativePathOf(DATA) ?: RELATIVE_PATH`；`relativePath = PathCase.canonicalizeDeep(rawRelative, volumeRoot)`；`path = File(volumeRoot, relativePath + name)`；`bucketName` 优先取校正后路径的父目录名（BUCKET_DISPLAY_NAME 同样可能带旧大小写）。
  - 旧行不需要额外的迁移：`isStoreStateChanged` 会比较 `relativePath`，下一轮增量同步会用 `updateStoreFields` 原地改写；`folderRows` 的 GROUP BY 自然合并成一个相册。
- 后果：路径解析需要多读若干次目录（有 60s 缓存），首次全量索引多花几秒；改名/移动过的目录下次同步自动纠正。
- 备选：直接用 `RELATIVE_PATH` 不做校正（用户看到的就是重复相册，否决）；全部改用 `File.listFiles` 遍历（Android 11+ 无法遍历 `Android/data`，且 10 万级慢得多，否决）。

## ADR-0046：视频索引只统计不动文件（v0.8）

- 状态：已采纳（2026-10-31，v0.8）
- 背景：用户要能看到手机里的视频总量，并希望它出现在文件夹页底部（虚拟文件夹），但明确"不要改视频位置"。
- 决策：
  - 新增 `video_item` 表（DB v6，`MIGRATION_5_6`：建表 + relativePath/dateTakenMs/sizeBytes/(isPresent,dateTakenMs) 四个索引），字段与 `media_item` 对齐但不含指纹列（视频不参与查重）。
  - `VideoDataSource.queryVideos(scope, onBatch): Boolean` 返回"是否完整查到结尾"：中途抛 `SecurityException`/`IllegalArgumentException` 返回 false，避免仓库把没看到的视频误标缺席。
  - `VideoRepository.syncFromMediaStore` 标缺席用三重守卫 `scanned > 0 && completed && hasFullVideoAccess()`：Android 14「仅选中的视频」只返回部分行，缺全量 `READ_MEDIA_VIDEO` 时绝不标缺席。每批一个事务 upsert，最后的 `markAllAbsent + markPresent` 也包在单事务里。

  - 视频只在「文件夹 → 视频」虚拟页里看数量/体积/时长/系统缩略图，点击用系统播放器 `ACTION_VIEW` 打开；不移动、不改名、不删除、不参与图片重复/相似分组。
- 后果：视频页的增量依赖后台同步或手动「刷新」；用户删光视频时旧行不会被清（与图片侧同样的保守取舍）；`video_item` 未来可复用给视频查重，但当前不做。

## ADR-0048：图库「全部展开/收起」用两级状态（v0.8）

- 状态：已采纳（2026-10-31，v0.8）
- 背景：v0.7 的「全部收起」只对已加载分组生效，用户下滑加载出新月份又是展开的。
- 决策：`GalleryScreen` 保留两个 `rememberSaveable` 状态——`collapseAll: Boolean` 与 `expandedUnderCollapseAll: Set<String>`；传给网格的折叠集合在 `remember(visibleGroupKeys, collapseAll, expandedUnderCollapseAll, collapsedGroupKeys)` 里算：
  `if (collapseAll) visibleGroupKeys - expandedUnderCollapseAll else collapsedGroupKeys`。
  「全部收起」置 `collapseAll = true` 并清空白名单；「全部展开」三项清空；单组点击在 `collapseAll` 期间改白名单，否则沿用旧的 `collapsedGroupKeys`。
- 后果：懒加载出来的新分组自动落进折叠集合；已知瑕疵是新键回报比组合晚一帧，新分组可能出现 1 帧展开态（转屏首帧同源）。
- 备选：把 `collapseAll` 判断下移到网格内部（能零帧，但要改网格的折叠契约，收益不抵改动面，暂不做）。

## ADR-0049：「找同角色」用 SauceNAO 结构化标签投票（v0.8）

- 状态：已采纳（2026-10-31，v0.8）
- 背景：v0.7 的找同角色只是把 SauceNAO/ascii2d 的**第一条标题**当角色名，用户反馈"效果很差"。
- 调研结论（`docs/search/角色识别调研-2026-10-31.md`）：Google Lens/豆包/Grok 靠大规模视觉 embedding + OCR + 知识图谱，端上无法复刻；最便宜的可用信号是 SauceNAO 返回的 `data.characters` / `data.material` / `data.creator`（人工标注 tag），不需要任何模型；WD14 tagger/danbooru 标签质量更好但要 30–300MB 模型 + ONNX，与"不加依赖"冲突，本版不采用。
- 决策：
  - `OnlineParsers.ParsedHit` 增 `characters/material/creator/source`（默认 null）；`OnlineHit` 同步增三字段。
  - 新增 `core/search/CharacterRecognition.kt`：`data class CharacterCandidate(name, score, source)` + `object CharacterRecognizer { fun candidates(hits, max = 8); fun splitNames(raw); fun topMaterial(hits) }`。
  - 权重 `characters 1.0 > material 0.7 > title 0.4 > creator 0.3`，每条命中再乘 `similarity/100`（缺省 0.5）；单条命中内同名只计一次（取权重最高的字段），跨命中累加；最后除以最高票归一化 → **相对分，不是置信度**。
  - 名称归一化：小写、下划线当空格、压缩空白（合并 `hatsune_miku` 与 `Hatsune Miku`）；只剥装饰性引号，不剥圆括号；19 个噪声词过滤（original/anime 等）。
  - `ImageSearchRepository.characterMatch()` 改为 SauceNAO + ascii2d 两家都问、全部命中喂投票器；`roleHint = candidates.firstOrNull()?.name`，`basis` 记录依据（"SauceNAO 命中 5 条，其中 3 条标注角色为…"）。
- 后果：角色候选主要来自 SauceNAO（ascii2d 现为 URL 模式、运行时不解析 HTML，标题基本拿不到）；UI 不显示百分比、不据此自动操作；最坏联网耗时约 40s（两家顺序请求）。
- 备选：端上跑 CLIP/ONNX 角色模型（体积与推理成本都不合适，否决）；把标题硬当角色名（就是 v0.7 的毛病，否决）。

## ADR-0053：回收站目录先做可写探测，失败按回退链换目录（v0.9）

- 状态：已采纳（2026-10-31，v0.9）
- 背景：用户遇到单张图片报「无法移入回收站：无法创建回收站目录」。根因有两层：① 旧代码是 `if (!dir.exists() && !dir.mkdirs()) 失败`，两个批次并发时后到的线程会因为「目录已被别人建好」而拿到 `mkdirs() = false`，被误判成不可写；② 部分 ROM/目录位置确实可能拒绝建目录或建得出但写不进。
- 决策：`TrashRepository` 新增 `resolveWritableTrashDir(root)`：候选按 `LinkedHashSet` 去重依次尝试「用户配置目录 → <卷根>/.EropicTrash → getExternalFilesDir(null)/trash → filesDir/trash」，每个候选走 `probeWritable(dir)`——`isDirectory`（并发已建好也算可用）或 `mkdirs()`，再真的 `createNewFile(".eropic-probe-<nano>.tmp")` 并删除，只有两步都通过才算可用。全部失败时 `OpFailure` 文案带上「已尝试 …、…」的绝对路径。新增 `effectiveTrashDir()`（回退后的实际目录）与 `trashDirCandidates()`（候选清单）供回收站页解释。
- 后果：并发 mkdirs 误判消失；卷根不可写时自动退到应用私有目录（同在内部存储，`rename` 依旧瞬时），不再丢文件；恢复仍按 `trash_item.originalPath` 搬回原处，与目录位置无关。代价是每次移入多做一次真实写探测（IO 线程，毫秒级）。
- 备选：只加重试（治不了目录真的不可写）；直接默认放应用私有目录（用户看不见、卸载即丢，否决）。

## ADR-0054：「保留本组」按成员落库，不清除就永久不再提示（v0.9）

- 状态：已采纳（2026-10-31，v0.9）
- 背景：用户要求「加一个保留按钮，即以后不考虑该组，并允许清除所有保留标记重新扫描」。
- 决策：新表 `ignored_member(mediaId PK, ignoredAtMs)`（DB v7 + `MIGRATION_6_7`，只有建表语句，不迁移数据）。按**成员**而不是按组记录：组的 `groupId` 每次重扫都会重写、成员也会随文件增删变化，按成员才稳定；一组里被保留的成员被过滤掉后不足 2 张，组自然不落库。`DuplicateScanner` 构造参数新增 `ignoredDao`：`scanExact` 在候选阶段就过滤忽略名单（连快速哈希都不读），`scanNear` 在分区前过滤。`EropicViewModel.ignoreGroup(groupId)` 只写标记表并立刻用 `deleteMembersForMedia + recomputeGroups + deleteMembersOfIncompleteGroups + deleteIncompleteGroups` 把该组从列表去掉；`clearIgnoredGroups()` 清表后重跑 `scanExact`/`scanNear`（只读指纹，几秒）。
- 后果：标记跨扫描、跨重启生效；清除标记要重扫（但不需要重新解码图片）。语义是「以后别再来烦我」，被保留的图也从精确重复里消失——若用户后悔，走「保留标记 N → 清除并重扫」。
- 备选：按 groupId 记录（扫描即失效，否决）；按文件路径记录（重命名/移动即失效，否决）。

## ADR-0055：差分图独立成 KIND_DIFF 分组，并从相似判定中排除（v0.9）

- 状态：已采纳（2026-10-31，v0.9）
- 背景：用户要求「相似逻辑加一个排除差分图功能，判定逻辑是前面字符完全相同、差别在最后的 p0/p1，并在重复相似等标签处加一个差分」。
- 决策：新增 `core/analysis/DiffImageDetector.kt`（纯 Kotlin，零 Android 依赖）：`baseKeyOf(displayName)` 用两条正则 `^(.*?)[ _\-]*[pP](\d{1,3})$` 与 `^(.*?)[ _\-]*差分[ _\-]*(\d{1,3})$` 取主体名，`baseKey = 主体小写 + "|" + 扩展名小写`；主体至少 2 个字符、数字 1~3 位（防 `photo_p2024` 年份误判）、扩展名不同不合并。`DuplicateScanner.scanNear` 改为先调 `partitionForNear(...)`（抽到 `NearPartitioning.kt` 以便纯 JVM 单测）：剔除忽略成员 → 挑出同 base 差分组 → 差分组以 `KIND_DIFF`（`maxDistance = 0`）落库 → 剩下的才跑 `NearDuplicateGrouper` 落 `KIND_NEAR`。差分不进「可释放空间」（每张通常都要留，算进去会高估）。清理页新增「差分」分类，质量卡标签显示「重复 / 相似 / 差分」。
- 后果：差分图不再被当成「相似可删」；索引完成文案多一段「差分 X 组」。局限：纯靠文件名，`img (1).png`、`img copy.jpg` 这类不识别，`xxx_p0` 也可能是真实文件名。
- 备选：用指纹聚差分（识别不了「同一主体不同版本」这种语义，否决）；不做差分只调阈值（用户明确要这个分类，否决）。

## ADR-0057：不复刻系统回收站（MediaStore IS_TRASHED）（v0.9）

- 状态：已采纳（2026-10-31，v0.9，结论性说明）
- 背景：用户问「每个手机应该都有自己的最近删除回收站地方吧，默认这个路径是不是更好」。
- 决策：继续用自建回收站（ADR-0013），**不**改用 `MediaStore.createTrashRequest` / `IS_TRASHED`。理由：① 移入必须走系统弹窗逐次确认（`MANAGE_MEDIA` 也不保证静默），批量操作不可接受；② 移入后条目对第三方 app 不再可读、拿不到缩略图，无法在应用内预览/批量恢复；③ 保留期由系统决定（约 30 天且不可配置），我们已有可配置保留期；④ 各家 ROM 的「最近删除」实现与展示差异大，行为不可控。手机上的系统回收站目录（MediaProvider 内部）本来就不对外暴露，也没有可写的公开路径，所以「用系统那个位置」在技术上做不到。
- 后果：回收站位置默认 `<卷根>/.EropicTrash`，可在回收站页改成 `Pictures/.EropicTrash`、`DCIM/.EropicTrash` 或自定义相对路径；不可写时按 ADR-0053 自动回退。

## ADR-0059：应用内更新补齐安装链路（安装权限 / 取消下载 / 删除安装包 / 发布时间）（v1.0）

- 状态：已采纳（2026-10-31，v1.0）
- 背景：用户 v0.7 实测点「安装更新」没反应（截图里只显示「安装包已下载 /data/user/0/…/cache/updates/Eropic-0.9.0.apk」），也不知道安装包会不会被清理。根因：Android 8+ 安装外部 APK 需要 `REQUEST_INSTALL_PACKAGES` + 用户授予「安装未知应用」，缺权限时 `startActivity` 静默失败。
- 决策：① Manifest 加 `REQUEST_INSTALL_PACKAGES`；② `installUpdate()` 先用 `packageManager.canRequestPackageInstalls()` 检查，未授权时把 `UpdateUiState.needsInstallPermission` 置真并提示，UI 显示「去授权」（`ACTION_MANAGE_UNKNOWN_APP_SOURCES`，`EropicViewModel.openInstallPermissionSettings()`）；③ 下载支持取消（`downloadCancelled` 标志 + `downloadJob.cancel()`，`UpdateChecker.download` 的写块循环里 `isCancelled()` 抛 `CancellationException`）；④ 支持删除已下载安装包（`deleteDownloadedUpdate()`），安装包路径可点击复制；⑤ `UpdateInfo.publishedAtMs` 从 `published_at` 解析（`Instant.parse` → `OffsetDateTime.parse` → 0 兜底）用于展示发布时间。
- 后果：安装包放在 `cacheDir/updates/`（系统可在存储紧张时清理，UI 明说「安装包保存在应用缓存目录，系统可能在存储紧张时清理它」）；判断「已是最新」只看 `updateAvailable`（版本名比较），**不**比 versionCode，因为本项目 versionCode 是构建时间戳。

## ADR-0064：联网识图改逐行列表 + 多图床回退链 + 部分引擎直传文件本体（部分取代 ADR-0041）（v1.0）

- 状态：已采纳（2026-10-31，v1.0；取代 ADR-0041 的「单一 litterbox 图床」与「FlowRow FilterChip 入口」两条）
- 背景：用户第 8/9 条：联网识图要改回一行一行的列表；SauceNAO 返回内容完全不对；IQDB / onegai.moe / lenso.ai / ascii2d 全部报「只接受公网图片链接，临时图床上传失败」；Google Lens 结果也不对。调研 `4evergr8/FlutterPicOrigin` 后确认它的做法是「先上传到自己 Cloudflare Worker 拿公网 URL，再用浏览器打开各引擎的结果页 URL」。
- 决策：① UI 侧由 `FlowRow` + `FilterChip` 改为 `OutlinedCard` 内逐行 `OnlineProviderRow`（名字 + 副标题 + 上传中转圈/右箭头，上传中禁用其余行）；② `ImageHost` 由单一 litterbox 改为四级回退链 `0x0.st → tmpfiles.org → uguu.se → litterbox`，返回 `UploadResult(url, attempted)`，失败文案列出每家原因并提示「可挂代理，或改用百度识图/ascii2d/IQDB（它们收文件本体，不需要图床）」；③ ascii2d、IQDB 改为 **multipart 直传文件本体**（respectively `https://ascii2d.net/search/file` 字段 `file`、`https://iqdb.org/` 字段 `file`，okhttp 跟随 302 拿最终页，用 `OnlineParsers.ascii2dHtml` / `iqdbHtml` 解析出 `items`），失败才退回图床 URL 模式；④ SauceNAO 仍走官方 API（内置 key），但 API 返回空条目时若图床可用则返回网页版结果页 URL；⑤ Google Lens 继续优先 URL 模式（`uploadbyurl`），图床不可用才回退 multipart；⑥ 成功时不再自动弹浏览器，结果在应用内列出，另有「在浏览器打开」。
- 后果：ascii2d / IQDB 在弱网下也能用（不依赖第三方图床）；onegai.moe / lenso.ai 仍必须有公网图片 URL，国内通常要代理；文字解析器（`OnlineParsers`）是非官方页面结构，站点改版会失效，但失败会退回「在浏览器打开结果页」。

## ADR-0065：本地识图改多特征加权评分（取代 ADR-0042 的颜色画像精排）（v1.0）

- 状态：已采纳（2026-10-31，v1.0；取代 ADR-0042 的「dHash/pHash 粗排 + ColorProfile 精排」）
- 背景：用户第 10 条「本地识图算法不好，你上网找一些更好的本地图片相似算法吧」。旧方案只有 dHash/pHash 汉明距离 + 12 桶色相直方图，缩放/换色/同角色不同姿势都容易漏。
- 决策：新建 `core/search/MultiFeatureSimilarity.kt`（纯 Kotlin，无 Android 依赖）：64 位 + 256 位感知哈希（0.30，其中 256 位占 0.6）+ 4×4 HSV 颜色布局相似度（0.40）+ 24 桶色相直方图与边缘密度（0.20）+ 长宽比（0.10），输出 0~100 与四项可解释分数（`SimilarImageHit.scores`）；`BitmapFeatures.kt` 把 Bitmap 采样到 64 长边；`CandidateBands.kt` 用 `hash_band` 倒排表按鸽笼原理取邻居（radius = maxDistance / 4，不丢召回）；`ImageSearchRepository` 流程改为「倒排候选 → dHash 粗排小顶堆 → 多特征精排 200 条 → `minSimilarity` 裁剪」。档位：严格 85 / 标准 70 / 宽松 55（`SimilarityQuery.minSimilarityFor`），ViewModel 用 `SimilarityQuery.atLevel(settings.similarity, keyword)` 接线。
- 后果：`hash_band` 为空的老索引会退回分页全表扫描（慢但结果正确，重新索引后恢复）；`VisualSimilarity.kt` 只剩自身单测引用，可后续删除；分数是**相对**参考图的重排依据，不是「同一张图」的概率。

## ADR-0066：诊断日志打包分享（LogCollector）（v1.0）

- 状态：已采纳（2026-10-31，v1.0）
- 背景：用户第 14 条「设置里加一个上传日志的功能，方便你帮我定位错误」。本项目无后端、无 INTERNET 之外的账号体系，不能真「上传」，改为「打包 + 系统分享」。
- 决策：`core/diagnostics/LogCollector.kt`：`collect(context, statsProvider)` 输出 `cacheDir/logs/eropic-log-<yyyyMMdd-HHmmss>.txt`（只保留最近 10 份），内容 = 应用版本/构建时间、设备与 ROM、权限状态、索引统计（`countPresent`/`countHashed`/回收站条数/重复组数）、最近 3 份崩溃日志、过滤后的 `logcat -d -t 800`（最多 500 行，只留本应用与系统媒体相关 tag）；`shareIntent(context, file)` 返回 ACTION_SEND。设置页「日志与反馈」卡：`collectLogsAndShare()` 生成后直接弹系统分享面板（用户自己选微信/邮件发给开发者），另有「清空日志」。
- 后果：日志里含文件路径与文件名（用户主动分享才出设备）；`file_paths.xml` 增加 `cache-path logs`；logcat 读取在 Android 10+ 受限于只读自己进程日志，因此主要价值是崩溃栈与统计快照。

## ADR-0067：关于页加联系邮箱、更新日志改成「版本 + 日期 + 逐条」（v1.0）

- 状态：已采纳（2026-10-31，v1.0）
- 背景：用户第 15/16 条：更新日志顺序不对、要加时间戳、内容不要太复杂且格式统一；关于页加邮箱 `Aemeath33@163.com`。
- 决策：`ui/about/Changelog.kt` 改为 `data class ChangelogEntry(version, date, items: List<String>)`，列表从 1.0.0 到 0.1.0 倒序，每条只有一个日期（`2026-10-28` / `2026-10-29` / `2026-10-31`），每个版本 3~6 条短句；`AboutScreen` 新增 `ContactCard`（`Intent.ACTION_SENDTO` + `mailto:`）；更新日志渲染为「版本号 + 日期」一行 + 逐条小字 + 分隔线。
- 后果：发布新版本时必须同时改 `Changelog.kt` 与 `appVersionName`，否则关于页与版本号不一致。

## ADR-0068：正式签名落地（keystore + keystore.properties + apksigner 校验）（v1.0.0）

- 状态：已采纳（2026-10-31，v1.0.0）
- 背景：v1.0.0 之前 release 一直回退 debug 签名，AD 版之间无法形成稳定升级链；用户要求「怎么弄正式签名，可以帮我弄一下吗」。
- 决策：用 `D:\jdk\jdk-17.0.12\bin\keytool.exe` 生成 `keystore/eropic-release.jks`（别名 `eropic`，RSA 2048，`-validity 10950` ≈ 30 年，`-dname "CN=Eropic, OU=Android, O=Eropic App, L=Shanghai, ST=Shanghai, C=CN"`）；口令写在项目根 `keystore.properties`（`storeFile/storePassword/keyAlias/keyPassword`），`*.jks` / `*.keystore` / `keystore.properties` 全部进 `.gitignore`；`app/build.gradle.kts` 按「`-P` 参数 → `keystore.properties` → 环境变量」取口令（注意脚本里的 `java` 是 Gradle 的 `JavaPluginExtension`，`Properties` 必须显式 `import java.util.Properties`，否则报 `Unresolved reference: util`）。
- 理由：侧载分发不需要 Play App Signing；自持密钥最简单，且能保证同一密钥连续覆盖升级；口令本地文件比命令行参数安全（不留在 shell history）。
- 后果：从 debug 签名的旧包迁到正式签名**必须卸载重装**（应用数据里的索引/设置会丢，照片与 `.EropicTrash` 里的文件不受影响）；密钥库或口令丢失会导致无法覆盖升级；`apksigner verify --print-certs` 可核对证书 SHA-256 `9C:B9:92:CE:8B:94:62:75:11:06:9A:DF:97:5F:9F:77:2F:17:84:31:7E:7F:94:0E:29:69:20:0C:1A:DF:50:A6`。
- 备选：`~/.gradle/gradle.properties` 存口令（跨项目共享、与仓库解耦，但换机器要另外拷）；把 keystore 提交进 git（绝对否决，泄露即被冒名更新）。
