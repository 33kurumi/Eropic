# 03 · 编码规范与协作约定

> 目的：一个人 + AI 长期迭代也能保持代码可读、可回滚、可维护；也给未来参与的开源贡献者一个明确标准。

## 1. 语言与注释

- 标识符、类名、包名：英文；用户可见文案：`strings.xml`（默认中文，英文后置）。
- 注释、commit、文档：中文。代码注释解释**为什么**（阈值来源、兼容性坑、性能取舍），不复述**是什么**。
- 复杂逻辑必须留"设计依据"：如 `// Hamming<=10 来自 200k 样本误报率 1e-8，见规划 5.5`。
- 不写"临时/先这样/以后再说"式注释；要么当时做对，要么开 TODO 带 Issue 编号。

## 2. Kotlin 规范

- 遵循 Kotlin 官方 style + ktlint（M1 接入，CI 里跑）。
- 禁止 `!!`；用 `requireNotNull / check / ?: error(...)`，异常信息带上下文。
- 状态用 `data class`；有限结果用 `sealed interface`（如 `AppResult`）。
- 体积/大小统一 `Long`（byte）；时间统一 epoch millis（UTC 存，显示层转本地时区）；不传 `File` 对象跨层，统一绝对路径 `String`。
- 公开函数显式写返回类型；顶层常量集中在 `object` 或 `companion object`，避免散落 magic number。
- 禁止全局可变状态；单例只放无状态服务（Repository/DataSource 由 Hilt 管理）。
- 可空性表达真实语义：数据库字段可空才用可空类型，不用 `0`/空串代表"未知"。

## 3. Compose 规范

- Composable 尽量无状态：状态提升到 ViewModel，事件用 lambda 上行。
- 收集状态用 `collectAsStateWithLifecycle()`，不用 `collectAsState()`。
- `LazyVerticalGrid/LazyColumn` 必须提供稳定 `key` 与 `contentType`；不要在 item 内创建新的 Modifier 链以外的重对象。
- 所有缩略图走统一 `MediaThumb`（Coil + 占位图 + 错误图），禁止页面各自加载。
- 副作用（LaunchedEffect/DisposableEffect）要能说清依赖；预览 `@Preview` 不放真实 IO。
- 文案全部走 `stringResource`，不硬编码中文到 Composable。

## 4. 协程与错误处理

- ViewModel：`viewModelScope`；Repository：`suspend` 函数；不向 UI 暴露 `Job`。
- UiState 四态：`Loading / Content / Empty / Error`；一次性事件（Toast/导航）用 `Channel` + `receiveAsFlow()`。
- Repository 返回 `AppResult<T>`（Success/Failure(code, message, cause)），不吞异常；网络/权限/IO 错误分类。
- 用户可见错误必须可行动："没有权限，去设置开启" > "操作失败"。
- 后台任务失败要可重试，不能把失败状态永久写死。

## 5. Git 与提交

- `main` 保持可编译、可安装；功能分支：`feat/<scope>`、`fix/<scope>`、`docs/<scope>`、`perf/<scope>`。
- 大功能分阶段合入，避免一个 PR 几千行。
- Conventional Commits（scope 用模块名，中文描述可）：
  - `feat(gallery): add timeline paging with stable keys`
  - `fix(trash): restore to suffixed path when target exists`
  - `perf(index): upsert 500 rows per transaction`
  - `docs(dev): add scaffold guide`
  - `test(hash): cover hamming boundary cases`
- 一个 commit 只做一件事；不提交 `build/`、`.idea/`、`local.properties`、`*.apk`、`*.iml`、缩略图缓存。
- 提交前跑：`.\gradlew.bat testDebugUnitTest`（M1 起加 lint）。

## 6. 自审清单（每次合并前）

- [ ] 编译 + 单元测试通过
- [ ] 无主线程 IO；无全表 COUNT；分页 key 稳定
- [ ] 权限被拒 / 14+ 部分授权有降级 UI
- [ ] 写操作有日志、失败回滚或"未完成"恢复入口
- [ ] 10 万条规模手测（模拟数据或真机）
- [ ] 文档同步：功能索引状态、功能开发文档、ADR（架构决策）
- [ ] 无未使用依赖；新增依赖有理由与 License 检查
- [ ] 没有把个人路径/手机号/账号写进代码或文档

## 7. 文档规则（"详细开发文档"的落地）

三层文档：

1. **产品规划**：`docs/Eropic-项目规划-v0.1.md` —— 需求、交互、技术方案、里程碑。
2. **开发总览**：`docs/dev/01~05` —— 环境、架构、规范、功能索引、决策记录。
3. **功能开发文档**：`docs/dev/features/<编号>-<名称>.md` —— 每个功能一份，模板见 `docs/dev/templates/功能开发文档模板.md`。

触发规则（硬性）：
- 新增/修改功能：更新 `04-功能索引.md` 的状态 + 对应功能开发文档。
- 表结构/接口/线程模型变化：同步更新 `02-架构与代码地图.md`。
- 重要选型（权限、存储、算法、回收站、模块拆分）：新增 ADR，不覆盖旧 ADR。
- 代码地图必须精确到文件与符号：`core/index/MediaScanner.kt#scanIncremental()`，禁止"在扫描模块里"这种模糊描述。

功能文档最少包含：目标与非目标、交互与状态、实现设计（数据流/关键类/线程/错误）、代码地图、测试与验收、已知限制、变更记录。

## 8. 依赖与 License

- 新增依赖先问：AndroidX/官方能否替代？体积/方法数/维护状态如何？
- 版本只在 `libs.versions.toml` 改，禁止散落硬编码。
- 参考开源项目只学交互与思路，**不复制 GPL/AGPL 代码**：Aves/Fossify 是 GPL，Immich/PhotoPrism 是 AGPL；本仓库代码原创。
- 本仓库 License 待定（建议 Apache-2.0 宽松，或 GPL-3.0 保持开源传染）；选定后加 `LICENSE` 与第三方许可清单。

## 9. 分支与发布（后续）

- 版本号语义化 `0.x.y`；每个 GitHub Release 附 APK + 变更说明 + 已知问题。
- 不上架商店，因此不需要 Play 政策适配；但**仍需适配各 ROM**（OriginOS/ColorOS/HyperOS/EMUI）的权限入口与后台限制。
- 发布前在 iQOO Neo8 上跑一遍：首启授权 → 扫描 10 万 → 重复分组 → 对比 → 移入回收站 → 恢复 → 卸载重装。
